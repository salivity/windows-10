Windows 10 64-Bit Kernel Memory and PTE Management

In the 64-bit edition of Microsoft Windows 10, the operating system manages memory using a hierarchical page-table architecture that translates 64-bit virtual addresses into physical memory locations. Kernel-mode Page-Table Entries (PTEs) serve as the fundamental data structures responsible for tracking this translation, controlling access privileges, and managing page states across physical RAM and secondary storage. This article details the structural mechanics of x64 PTEs in Windows 10, including the multi-level translation hierarchy, PTE state tracking, dynamic self-referencing page-table mechanisms, and security features like Kernel Virtual Address Shadowing (KVAS).

Multi-Level Page-Table Hierarchy

Windows 10 on the x64 architecture primarily utilizes 48-bit virtual addressing, structured through a four-level paging hierarchy. The virtual address space is split evenly into two 128 TB regions: user space (lower half) and kernel space (canonical upper half, typically beginning at 0xFFFF800000000000).

To translate a 64-bit virtual address, the processor uses the hardware-defined CR3 control register, which holds the base physical address of the initial root table. The translation spans four distinct structures:

  1. Page Map Level 4 (PML4): Bits 47–39 index into the PML4 table to locate a Page Directory Pointer Table (PDPT).
  2. Page Directory Pointer Table (PDPT): Bits 38–30 index into the PDPT to locate a Page Directory (PD).
  3. Page Directory (PD): Bits 29–21 index into the PD to locate a Page Table (PT).
  4. Page Table (PT): Bits 20–12 index into the PT to pinpoint the exact Page-Table Entry (PTE).
  5. Page Offset: Bits 11–0 provide the direct byte offset within the selected 4 KB physical frame.

If large pages are used (such as 2 MB pages for the kernel image or high-performance pools), the PD entry points directly to a 2 MB physical frame, bypassing the PT stage entirely.

Hardware vs. Software PTE Structure

A 64-bit PTE occupies 8 bytes (64 bits). Its internal bit layout changes dynamically depending on whether the target page currently resides in physical RAM.

Valid (Hardware) PTEs

When the least significant bit (Bit 0, the Present bit) is set to 1, the CPU hardware Memory Management Unit (MMU) handles translation directly. Key bits include:

  • Present (P, Bit 0): Must be 1 for the page to be valid in RAM.
  • Read/Write (R/W, Bit 1): Configures read-only or read/write access.
  • User/Supervisor (U/S, Bit 2): Enforces isolation; set to 0 for kernel-mode pages to prevent user-mode execution or access.
  • Page-level Write-Through and Cache-Disable (PWT/PCD, Bits 3–4): Controls caching policies.
  • Accessed and Dirty (A/D, Bits 5–6): Set by hardware when the page is read or written.
  • Physical Frame Number (PFN, Bits 12–47): Contains the upper bits of the physical address pointing to the 4 KB page frame.
  • No-Execute / Execute-Disable (NX/XD, Bit 63): Mitigates exploitation by marking data pages as non-executable.

Invalid (Software) PTEs

When Bit 0 is 0, referencing the address triggers a page fault (Interrupt 14). The Windows Memory Manager intercepts this fault and interprets the remaining 63 bits as custom software flags. Software PTEs fall into several categories:

  • Demand-Zero: Instructs the kernel to allocate a fresh, zeroed physical frame on first access.
  • Transition: The page is present in physical memory (e.g., on the modified or standby list) but marked invalid to force a soft fault, which quickly restores the valid state.
  • Pagefile: Contains indices indicating which pagefile and disk block stores the swapped-out content.
  • Prototype PTEs: Pointers to unified structures used for shared resources, such as memory-mapped files and shared DLL sections, ensuring multiple processes map to identical physical backing stores without duplicating allocation metadata.

Dynamic Self-Referential Page Tables

Prior to Windows 10, the operating system used a predictable self-referencing PML4 entry (traditionally index 0x1ED, mapping the page directory tables at virtual address 0xFFFFF68000000000). This static mapping allowed kernel code to calculate the virtual address of any page-table structure efficiently, but it became a primary target for kernel exploitation.

Beginning with Windows 10, Microsoft introduced randomized self-referential entries. During boot initialization, the Memory Manager selects a random PML4 slot to point back to the PML4 itself. Because this self-map address changes with every system restart, exploit payloads cannot rely on hardcoded page-table base addresses to manipulate PTE permissions (such as toggling the Read/Write or NX bits).

Page Frame Number (PFN) Database Synchronization

Every valid PTE coordinates with the Windows PFN database (nt!MmPfnDatabase), an array of structures that stores metadata for every physical page in RAM. When a PTE is updated, the kernel updates the associated MMPFN entry to reflect state changes, reference counts, and the original virtual address.

When modifying PTE attributes (such as unmapping a page or marking it invalid), the operating system issues an INVLPG (Invalidate Page) instruction or a multi-processor inter-processor interrupt (IPI) to flush stale translations from the CPU's Translation Lookaside Buffer (TLB).

Kernel Virtual Address Shadowing (KVAS)

To mitigate side-channel speculative execution vulnerabilities (such as Meltdown), modern builds of 64-bit Windows 10 implement Kernel Virtual Address Shadowing.

Under KVAS, the system maintains two separate PML4 translation tables for each user process:

  • User PML4: Active when code executes in ring 3. It maps the user-mode address space, but masks almost all kernel-mode memory, exposing only minimal entry-point stubs and interrupt-handling tables required to transition into the kernel.
  • Kernel PML4: Loaded into the CR3 register upon entry to ring 0 via system calls or hardware interrupts. This table contains the complete, unshadowed view of kernel-space PTEs.

By segmenting the kernel PTE landscape across isolated CR3 contexts, Windows 10 prevents speculative hardware operations in user mode from probing protected kernel memory structures.
