Windows 10 Multi-Homed DNS Resolution Priority

This article explains how Microsoft Windows 10 resolves Domain Name System (DNS) queries when connected to multiple networks simultaneously, a configuration known as multi-homing. It details the underlying mechanism of Smart Multi-Homed Name Resolution, the role of network interface metrics, the query dispatch process, and the administrative controls available to prevent DNS leaks and manage lookup behavior.

Smart Multi-Homed Name Resolution (SMHNR)

In Windows 10, standard DNS resolution for multi-homed devices is governed by a feature called Smart Multi-Homed Name Resolution (SMHNR). Unlike legacy versions of Windows that queried network adapters sequentially based strictly on adapter binding order, Windows 10 optimizes for speed by default.

When an application requests a domain lookup, the Windows DNS client does not simply wait for a primary adapter to fail before trying secondary adapters. Instead, it sends the DNS request to all configured network interfaces—including physical Ethernet, Wi-Fi, and active Virtual Private Network (VPN) adapters—simultaneously or in rapid succession. The operating system accepts whichever valid response arrives first and discards the slower responses.

Interface Metrics and Priority Ordering

While SMHNR facilitates parallel querying, Windows 10 still maintains an internal hierarchy determined by the IPv4 and IPv6 Interface Metric.

  1. Automatic Metric Calculation: By default, Windows assigns an interface metric to each adapter based on link speed. Higher-speed connections (such as gigabit Ethernet) receive lower metric values, while slower connections (such as Wi-Fi or cellular) receive higher metric values.
  2. Preferred Dispatch: The DNS client initially prioritizes DNS servers configured on the adapter with the lowest metric.
  3. Parallel Fallback: If the preferred adapter does not return a successful answer within a brief threshold (typically around 1 second), queries are dispatched to all other active network adapters concurrently.

Because the fastest server wins, a public DNS server on a local Wi-Fi network may respond before an internal corporate DNS server across a VPN tunnel, leading to unexpected resolution results.

Resolution Flow and Negative Responses

The behavior of SMHNR is specifically tailored to handle negative responses:

  • NXDOMAIN (Non-Existent Domain): If the highest-priority adapter returns an NXDOMAIN response, Windows 10 does not stop. It allows parallel queries on other adapters to complete to determine if the domain exists on another connected network (such as an internal corporate intranet).
  • Timeouts: If an adapter fails to respond due to network latency or packet loss, the operating system relies on responses from any other interface that successfully returns a record.
  • Fallback Protocols: If all configured DNS servers across all interfaces fail to resolve the name, Windows falls back to broadcast protocols, such as Link-Local Multicast Name Resolution (LLMNR) and NetBIOS over TCP/IP (NetBT).

Security and Privacy Implications

The aggressive parallel nature of multi-homed resolution introduces the risk of DNS leakage. In split-tunnel VPN scenarios, internal company domain names may be queried against public ISP DNS servers, potentially exposing confidential hostnames to third parties. Conversely, public internet lookups might be intercepted or routed through private networks.

Managing and Disabling Multi-Homed DNS Behavior

Administrators can force Windows 10 to behave sequentially or restrict queries to preferred interfaces using Group Policy or the Windows Registry.

Group Policy

To enforce sequential lookups and avoid parallel broadcasting:

  1. Open gpedit.msc.
  2. Navigate to: Computer Configuration > Administrative Templates > Network > DNS Client.
  3. Enable the policy: Turn off smart multi-homed name resolution.

Registry

The same configuration can be applied directly to the registry:

  • Path: HKEY_LOCAL_MACHINE\Software\Policies\Microsoft\Windows NT\DNSClient
  • Name: DisableSmartNameResolution
  • Type: REG_DWORD
  • Value: 1 (Disables SMHNR, restoring sequential querying based on interface metrics)

Setting this value ensures that queries are directed exclusively to the DNS servers associated with the primary network adapter, querying secondary interfaces only if the primary servers fail to respond.
