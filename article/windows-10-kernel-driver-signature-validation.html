Windows 10 Kernel Driver Signature Validation

To protect system integrity and prevent rootkits from compromising the operating system, Microsoft Windows 10 mandates that all kernel-mode drivers be cryptographically validated before execution. This security mechanism relies on Kernel Mode Code Signing (KMCS) enforced through a chain of trust that begins at firmware startup and passes through the Windows Boot Manager, the Windows OS Loader, and the kernel itself. By checking digital signatures against trusted root certificates, Windows 10 ensures that driver code has not been tampered with and originates from a verified, Microsoft-approved publisher before it ever executes in Ring 0.

The Chain of Trust: UEFI and Secure Boot

The validation process begins before Windows even initializes. If Secure Boot is enabled within the UEFI firmware, the system authenticates the boot environment using OEM-enrolled keys.

  1. The firmware verifies the signature of the Windows Boot Manager (bootmgr.efi).
  2. The Boot Manager loads and validates the Windows OS Loader (winload.efi).
  3. winload.efi takes ownership of validating early-launch components, boot-start drivers, and the kernel itself (ntoskrnl.exe).

Authenticode and Catalog File Verification

Every kernel driver package consists of the binary file (.sys) and an optional security catalog (.cat). When checking a driver:

  • Embedded Signatures: Boot-start drivers required for initial initialization must contain an embedded Authenticode signature within the PE (Portable Executable) header.
  • Catalog Files: Non-boot drivers can store their signature in a catalog file, which contains a collection of cryptographic hashes for the driver package files.

The loader reads the driver's binary, computes its cryptographic hash (typically SHA-256), and compares it to the digest encrypted inside the digital signature. If the computed hash matches the decrypted hash, the file's integrity is confirmed, proving it has not been modified since it was signed.

Certificate Hierarchy and Microsoft Signing Authorities

Windows 10 strictly regulates which Certificate Authorities (CAs) are trusted for kernel execution. Starting with Windows 10 version 1607, standard third-party commercial certificates are no longer sufficient for kernel loading on 64-bit systems.

  1. Microsoft WHQL / Partner Center: The driver must be submitted to the Microsoft Hardware Developer Center Dashboard. Microsoft signs the driver package using the Microsoft Windows Hardware Compatibility Program CA or an Attestation signing certificate.
  2. Root CA Validation: winload.efi and the Windows kernel trace the signature’s certificate path back to the Microsoft Root Certificate Authority.
  3. Cross-Certificates (Deprecation): In legacy configurations or older builds, cross-certificates tied to Microsoft’s root were accepted, but modern Windows 10 systems enforce a direct Microsoft signature.

Driver Signature Enforcement (DSE)

Driver Signature Enforcement is the kernel-level gatekeeper. Before calling the DriverEntry routine of any driver:

  • The loader evaluates the code integrity flags.
  • DSE checks revocation lists, including the Driver Revocation List (a component of Windows Defender Application Control) and Certificate Revocation Lists (CRLs), to confirm the signing key has not been compromised.
  • If a signature is missing, expired without a valid timestamp, untrusted, or modified, DSE aborts the load process. On boot-start drivers, this results in a system halt (Bug Check / Blue Screen of Death); for runtime drivers, the system logs an event (such as Event ID 5038) and returns an access-denied status (STATUS_INVALID_IMAGE_HASH).

Hypervisor-Protected Code Integrity (HVCI)

In enterprise and modern Windows 10 configurations using Virtualization-based Security (VBS), driver validation is supplemented by Hypervisor-Protected Code Integrity (HVCI). Under HVCI, code integrity runs inside an isolated virtual machine (Virtual Secure Mode) created by the Windows hypervisor. The hypervisor enforces Second Level Address Translation (SLAT) permissions to ensure that pages marked as executable cannot be modified, preventing even an exploited kernel from dynamically altering or executing unsigned driver code in system memory.
