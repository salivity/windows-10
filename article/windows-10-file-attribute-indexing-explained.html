Windows 10 File Attribute Indexing Explained

This article explains how the Microsoft Windows 10 operating system processes, catalogs, and retrieves file attributes to deliver rapid results through Windows Search. It details the underlying architecture of the Windows Search service, how the Extensible Storage Engine (ESE) database structures metadata, the role of the NTFS Change Journal in tracking modifications, and how property handlers extract file attributes for instant query resolution.

The Windows Search Service Architecture

At the core of file indexing in Windows 10 is the Windows Search service (WSearch), a background system service that runs with elevated system privileges. Rather than scanning the storage drive sequentially every time a user types a query, Windows 10 maintains a persistent, pre-computed catalog of files, paths, and metadata.

The service operates in low-priority I/O and CPU modes to avoid degrading overall system performance. It monitors user activity and throttles indexing tasks during intensive system usage or when a laptop is running on battery power.

The Extensible Storage Engine (Windows.edb)

All indexed file attributes and contents are stored in an Extensible Storage Engine (ESE) database, commonly known as Jet Blue. This database is located on the system drive at:

C:\ProgramData\Microsoft\Search\Data\Applications\Windows\Windows.edb

The ESE database functions as a high-performance, B-tree structured database capable of handling millions of records. Within this database, file attributes—such as file name, file path, size, date created, date modified, extension, and file flags (read-only, system, hidden)—are mapped as structured columns. For text-based files, the database also maintains an inverted index that maps specific terms to file IDs for fast full-text search.

Tracking File Changes with the NTFS USN Journal

To prevent continuous, resource-heavy directory scanning, Windows 10 relies directly on the NTFS file system’s Update Sequence Number (USN) Change Journal.

Whenever a file is created, modified, deleted, or has its attributes altered, the NTFS driver writes a record of this action to the USN Journal. The Windows Search service monitors this journal. When a change is detected:

  1. The service identifies the exact file referenced by the USN record.
  2. It fetches the updated file system attributes.
  3. It updates the corresponding record in Windows.edb without touching the rest of the storage volume.

Attribute Extraction and Property Handlers

Windows Search differentiates between basic file system attributes and extended file properties:

  • Standard File System Attributes: Basic metadata like file size, directory path, timestamps, and attributes (e.g., archive, compressed) are obtained directly from the Master File Table (MFT) of the file system.
  • Extended Properties: Windows uses modular components called Property Handlers to read internal metadata. For example, image files (EXIF tags such as dimensions and camera model), audio tracks (ID3 tags like artist and bitrate), and Office documents (author, word count) are parsed by their respective handlers and added to the indexed attribute columns.
  • Content Extraction: If content indexing is enabled for a given file type, an IFilter interface is invoked to strip formatting and parse raw textual data into the inverted index.

Indexing Modes: Classic vs. Enhanced

Windows 10 provides two operational modes for file indexing:

  • Classic Search: Focuses indexing strictly on common user profile locations (Desktop, Documents, Pictures, Music, and Videos) and explicit inclusions set by the user.
  • Enhanced Search: Expands the scope across all non-system, non-hidden partitions and directories on the PC, indexing metadata across the entire storage space while respecting standard exclusion rules (such as temporary folders and the OS system directory).

Fast Query Resolution

When a user initiates a query through the taskbar or File Explorer, Windows Search translates the query into an indexed search against Windows.edb. Because the B-tree structure provides logarithmic time complexity (\(O(\log n)\)) for lookups, the operating system can scan millions of file attributes in milliseconds, instantly returning matching files filtered by name, size, type, or date.
