How Windows 10 Handles UAC Token Elevation

This article explains how the Microsoft Windows 10 operating system manages user token elevation within the User Account Control (UAC) pipeline. It details the underlying mechanism of split administrative tokens, the specific triggers that detect an application's need for elevation, the system services that broker the request, and how the kernel securely launches elevated processes without compromising system integrity.

The Dual-Token Architecture

When an administrative user logs into Windows 10, the Local Security Authority (LSA) creates two separate access tokens for that logon session:

  1. Filtered Standard User Token: Stripped of administrative privileges and specific access rights (such as SeDebugPrivilege). This token runs normal shell operations, desktop environments, and everyday applications.
  2. Linked Full Administrator Token: Contains the complete set of administrative groups and privileges granted to the user. This token remains dormant and isolated until explicitly summoned by an elevation trigger.

Standard non-administrative accounts generate only a single restricted token. For these users, elevation requires "Over-the-Shoulder" (OTS) credentials, where an administrator's explicit username and password must be supplied.

Detection and Elevation Triggers

Windows 10 monitors process creation for specific triggers that indicate an application requires elevated access:

  • Application Manifests: Developers embed an XML manifest defining the requestedExecutionLevel. Values include asInvoker (default privilege), highestAvailable (elevates automatically if the user is an admin), and requireAdministrator (always demands elevation).
  • Installer Detection Heuristics: If an executable lacks a manifest, Windows evaluates the filename and file properties for installer-related keywords (such as setup, install, update, or patch). It also checks for common installation engine metadata (such as InstallShield or Wise).
  • Explicit User or Programmatic Actions: Users can invoke elevation via the "Run as administrator" context menu item. Programmatically, applications call the ShellExecuteEx Windows API with the runas verb.
  • Compatibility Database (Shim Engine): The Application Compatibility (AppCompat) database contains predefined flags that force elevation for legacy software known to fail without administrative rights.

The AppInfo Broker and Consent Architecture

Once a trigger is flagged, the initiating process cannot elevate itself directly. Windows 10 relies on an isolated inter-process communication pipeline:

  1. RPC Request to AppInfo: The shell delegates the execution request via Remote Procedure Call (RPC) to the Application Information Service (Appinfo.dll), which runs inside a shared Service Host (svchost.exe) under the LocalSystem account.
  2. Secure Desktop and Consent UI: Appinfo launches the Consent interface (consent.exe). This interface is displayed on the "Secure Desktop"—an isolated desktop space (Winlogon desktop) inaccessible to applications running on the user's interactive desktop. This isolation blocks UI spoofing, keystroke logging, and simulated mouse events (Shatter attacks).
  3. Validation and Digital Signatures: consent.exe validates the target binary's Authenticode signature. If signed by a trusted publisher, the prompt displays a blue banner; if unsigned or untrusted, it displays an amber warning banner.

Process Creation and Token Assignment

After the user approves the prompt (or successfully enters administrative credentials in an OTS scenario):

  1. Token Retrieval: The Appinfo service retrieves the linked full administrator token associated with the user's logon session.
  2. Process Spawning: Appinfo calls the kernel API CreateProcessAsUser (or CreateProcessWithTokenW), supplying the full administrator token.
  3. Parentage Decoupling: Because the service spawns the process, the new elevated process does not inherit the standard user token of the shell that launched it. However, Windows re-parents the environmental pointers so the new process visually appears within the user's standard desktop session.

If the user denies the prompt, the pipeline terminates, and the initiating process receives an access-denied error (ERROR_CANCELLED). Through this structured pipeline, Windows 10 ensures that standard processes remain contained and administrative power is only exercised through deliberate, validated actions.
