How Windows 10 Isolates VMs Using VBS

Virtualization-Based Security (VBS) in Windows 10 uses hardware virtualization features to create a secure memory enclave isolated from the primary operating system. This article explains the underlying architecture of VBS, how it leverages the Hyper-V hypervisor to create Virtual Trust Levels (VTLs), and the specific mechanisms used to isolate security-critical operations, system processes, and micro-virtual machines from the standard Windows environment.

The Hyper-V Foundation

At the core of VBS is the Microsoft Hyper-V hypervisor. When VBS is enabled, Windows 10 does not run directly on the physical hardware. Instead, the hypervisor sits directly above the hardware layer, leveraging CPU-level virtualization extensions (Intel VT-x or AMD-V). The hypervisor partitions system resources and governs access between the underlying hardware and the software running on top of it.

Virtual Trust Levels (VTLs)

VBS uses the hypervisor to divide the operating system environment into two distinct execution domains known as Virtual Trust Levels:

  • VTL 0 (Normal World): Runs the standard Windows 10 operating system, including the typical Windows NT kernel, system drivers, user applications, and standard virtual machines.
  • VTL 1 (Secure World): An isolated execution environment running a stripped-down, hardened "Secure Kernel." VTL 1 operates with higher privileges than VTL 0.

Isolation is strictly one-directional: code executing in VTL 1 can inspect and modify resources in VTL 0, but software running in VTL 0—even code with full kernel-level (Ring 0) administrator privileges—cannot read, modify, or execute code inside VTL 1.

Memory Protection via SLAT

To enforce memory isolation between these levels, the hypervisor utilizes Second-Level Address Translation (SLAT), implemented as Extended Page Tables (EPT) on Intel processors or Nested Page Tables (NPT) on AMD processors.

The hypervisor manages physical memory mapping independently of the VTL 0 OS kernel. Even if malware completely compromises the standard Windows kernel, it cannot modify the hypervisor-controlled page tables. Any attempt by VTL 0 to access memory ranges allocated to VTL 1 or protected micro-VMs generates an intercept fault, causing the CPU to trap execution into the hypervisor, which blocks the unauthorized access.

Hypervisor-Protected Code Integrity (HVCI)

VBS protects the boundaries of virtualized spaces using Hypervisor-Protected Code Integrity (HVCI). HVCI runs inside VTL 1 and validates all kernel-mode drivers and system files before they are allowed to execute in VTL 0. HVCI enforces the W^X (Write XOR Execute) rule on memory pages: a page can be writable or executable, but never both simultaneously. This prevents malicious actors from injecting unsigned, arbitrary code into executable system memory.

Isolating Micro-VMs and Sandboxes

The architecture that powers VBS also enables application-level isolation features, such as Windows Sandbox and Microsoft Defender Application Guard (WDAG). Instead of running inside the standard user space, these features deploy lightweight "micro-VMs" (Utility VMs).

These micro-VMs operate as separate guest partitions managed directly by the hypervisor:

  • Dedicated Virtual Memory: Micro-VMs receive separate address spaces governed by the hypervisor, preventing data leakage back to the host system.
  • Stripped Hardware Access: The micro-VM communicates with the host OS only through strict, secured virtualization channels (VMBus), limiting potential attack vectors.
  • Ephemeral Lifecycle: Once closed, the micro-VM and its memory state are discarded entirely, ensuring no residual code persists into the host or other running instances.
