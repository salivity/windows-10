How Windows 10 Encrypts the Pagefile

The Microsoft Windows 10 operating system provides built-in mechanisms to encrypt the paging file (pagefile.sys), safeguarding volatile memory data temporarily offloaded to persistent storage. This article explores why pagefile encryption is critical for data security, how Windows 10 handles this process natively at the filesystem level, the role of BitLocker, and how to verify and configure the feature.

The Security Risk of the Windows Pagefile

The paging file acts as a secondary reservoir for Random Access Memory (RAM). When physical memory is depleted or when memory pages are inactive, the Windows Memory Manager writes these pages to the storage drive in a hidden system file named pagefile.sys.

Because this volatile memory frequently holds sensitive data—including plaintext passwords, cryptographic keys, personal identifiable information (PII), and session tokens—storing it unencrypted on a physical disk exposes the system to offline attacks. An attacker with physical access to the machine could bypass Windows security permissions by booting into a secondary operating system or mounting the drive externally to read the contents of pagefile.sys.

Native Pagefile Encryption via the File System

Windows 10 provides native, kernel-level encryption for the paging file independent of full-disk encryption solutions. This feature relies on the Encrypting File System (EFS) architecture integrated within the NTFS driver.

When native pagefile encryption is active:

  1. Ephemeral Key Generation: During each boot sequence, the Windows kernel generates a unique, symmetric encryption key in volatile memory.
  2. On-the-Fly Encryption: The memory manager and storage stack encrypt all outgoing data blocks before writing them to pagefile.sys. Conversely, blocks read from the pagefile into active RAM are decrypted dynamically.
  3. Session-Bound Security: Because the encryption key exists solely in physical RAM and is never committed to persistent storage, it vanishes upon shutdown or restart. An adversary extracting the drive cannot decrypt the leftover pagefile data because the cryptographic key is permanently lost.

Integration with BitLocker Drive Encryption

In enterprise and modern consumer environments, full-volume encryption via BitLocker is the primary defense mechanism. When BitLocker is enabled on the operating system volume (typically the C: drive), all files residing on that volume—including pagefile.sys and the hibernation file (hiberfil.sys)—are encrypted at the sector level using XTS-AES.

While BitLocker completely protects the pagefile on the system drive, native pagefile encryption remains essential if the administrator configures the paging file to reside on a secondary, unencrypted partition or physical drive.

Enabling Native Pagefile Encryption

Native pagefile encryption is disabled by default in standard Windows 10 installations. Administrators can enable it using the fsutil command-line utility via an elevated Command Prompt:

fsutil behavior set EncryptPagingFile 1

To verify the current status of the setting, execute:

fsutil behavior query EncryptPagingFile

A return value of 1 indicates that pagefile encryption is enabled, while 0 indicates it is disabled. A full system restart is required for the change to take effect, allowing the kernel to allocate and begin encrypting memory pages under the newly initialized key.

Performance Impact

Modern processors feature hardware-assisted AES acceleration (such as Intel AES-NI and AMD AES extensions). As a result, the overhead introduced by encrypting and decrypting memory pages during swap operations is negligible for the majority of workloads, providing a high level of physical data protection with minimal performance cost.
