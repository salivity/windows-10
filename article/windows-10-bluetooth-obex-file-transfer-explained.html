Windows 10 Bluetooth OBEX File Transfer Explained

This article provides an overview of how the Microsoft Windows 10 operating system implements and manages Bluetooth Object Exchange (OBEX) protocols for wireless file transfers. It covers the underlying architectural stack, the specific profiles used for communication, the security mechanisms governing incoming and outgoing payloads, and the function of native system utilities like fsquirt.exe in handling data transactions.

The OBEX Protocol and Supported Profiles

Object Exchange (OBEX) is a binary communications protocol that enables systems to exchange binary objects in a standardized manner. In Windows 10, OBEX operates primarily over the RFCOMM (Radio Frequency Communication) layer, which emulates serial port connections over the core Bluetooth Logical Link Control and Adaptation Protocol (L2CAP).

While OBEX can support multiple application-level profiles, Windows 10 relies almost exclusively on the Object Push Profile (OPP) for generic ad-hoc file transfers. Unlike the broader File Transfer Profile (FTP)—which allows client-side browsing of remote directory structures and is largely deprecated or unsupported in modern native Windows stacks—OPP functions as a simple push-and-pull mechanism designed for sending individual or small batches of files between paired or discoverable devices.

Outgoing File Transfers (Pushing Data)

When an outgoing transfer is initiated from Windows 10, the operating system executes the following steps:

  1. Service Discovery: Windows uses the Service Discovery Protocol (SDP) to query the target device for an active OPP service record and determine the appropriate RFCOMM channel.
  2. Connection Establishment: The Windows Bluetooth stack opens an RFCOMM session to the destination channel.
  3. OBEX Connect: The OS sends an OBEX CONNECT packet containing the maximum packet size (MTU) it can handle.
  4. Data Transmission: The file is transmitted via a sequence of OBEX PUT requests. The payload includes metadata (such as the filename and file size) followed by chunks of the file's binary data.
  5. Termination: Once the target device acknowledges the final chunk (PUT with the final bit flag set), Windows sends an OBEX DISCONNECT packet and tears down the underlying RFCOMM channel.

Incoming File Transfers and fsquirt.exe

Windows 10 implements strict security measures regarding incoming OBEX connections to prevent unauthorized access and drive-by payloads. By default, the system does not run a persistent background OBEX server listener that automatically accepts files from remote devices.

To receive files via Bluetooth, the user must explicitly set the operating system into a listening state. This is typically handled through the Windows Bluetooth File Transfer application (fsquirt.exe):

  1. User Initiation: When the user selects "Receive files" from the Bluetooth system tray or settings menu, Windows launches fsquirt.exe.
  2. Listener Activation: The application registers an active OPP server entry via SDP and binds a listener to an available RFCOMM channel.
  3. Incoming Handshake: When the remote device pushes a file, Windows processes the initial OBEX PUT request to extract the file name, type, and size.
  4. Temporary Staging: The payload is received and buffered into a temporary directory within the user's local profile (AppData\Local\Temp).
  5. Commitment to Disk: The user is prompted with a dialog to accept the file and choose a destination path. If accepted, the file is moved to the target directory; if declined or if the connection times out, the cached temporary data is purged.
  6. Listener Teardown: Once the wizard is closed, the SDP record is unregistered, and the RFCOMM port stops listening.

Security and Pairing Enforcement

Windows 10 manages OBEX transfers through the standard Windows security boundary:

  • Authentication: While OPP theoretically allows transfers between unpaired devices, Windows 10 generally requires devices to be paired via Secure Simple Pairing (SSP) using numeric comparison or passkeys before an OBEX data stream is permitted.
  • Malware Mitigation: Because incoming transfers are piped through user space via the shell rather than executed directly by the kernel stack, Windows Defender and third-party antivirus software scan the staged files immediately upon reception before they can be executed by the user.
