How Credential Guard Stops Windows 10 Credential Dumping

Windows Defender Credential Guard protects Windows 10 environments by isolating critical authentication secrets to prevent credential theft attacks, such as Pass-the-Hash and Pass-the-Ticket. By leveraging hardware virtualization, this feature removes secrets from the standard operating system memory and places them in a protected virtual container. This article explains the architectural mechanics of Credential Guard, how it alters traditional authentication storage, and why it effectively blocks credential dumping tools.

The Traditional Credential Dumping Threat

In standard Windows architectures, the Local Security Authority Subsystem Service (lsass.exe) manages active user credentials, Kerberos tickets, and NTLM hashes in its process memory. If an attacker gains administrative or SYSTEM-level privileges on a workstation, they can inspect or dump this memory using tools like Mimikatz. With direct access to lsass.exe, attackers extract cached credentials and move laterally across an enterprise network.

The Role of Virtualization-Based Security (VBS)

Windows Defender Credential Guard mitigates this vector using Virtualization-Based Security (VBS). VBS relies on the Windows Hyper-V hypervisor to divide the physical system into two distinct virtual execution environments:

  • Virtual Trust Level 0 (VTL 0): The standard execution environment where the Windows 10 operating system, standard kernel, third-party drivers, and user applications run.
  • Virtual Trust Level 1 (VTL 1): A separate, secure virtual environment known as Isolated User Mode (IUM), completely inaccessible to VTL 0, even by processes with full kernel-level permissions.

Isolating the Local Security Authority (LsaIso)

Credential Guard divides the traditional tasks of the Local Security Authority between VTL 0 and VTL 1:

  1. Standard LSA (lsass.exe): Continues to run in VTL 0 to interact with applications, but it no longer stores plaintext secrets, NTLM password hashes, or Kerberos Ticket Granting Tickets (TGTs).
  2. Isolated LSA (LsaIso.exe): Runs inside the protected VTL 1 environment. It assumes sole custody of high-value authentication secrets and performs cryptographic operations within this secure container.

When lsass.exe in the primary operating system requires an authentication token, it sends a Remote Procedure Call (RPC) to LsaIso.exe. The isolated process performs the necessary cryptographic tasks in VTL 1 and returns only the required result or a non-sensitive proxy token back to VTL 0. The actual credentials never leave the isolated environment.

Blocking Attack Tools and Privilege Escalation

Because the hypervisor enforces memory separation at the hardware level, the standard Windows kernel running in VTL 0 cannot map, read, or alter the memory allocated to VTL 1.

Even if an attacker achieves full SYSTEM access or installs a malicious kernel-level driver in Windows 10:

  • Calls to APIs like OpenProcess or ReadProcessMemory targeting lsass.exe return empty or non-sensitive data because the target secrets are not present in VTL 0.
  • Direct hardware and memory read attempts into VTL 1 are blocked by the CPU's Second Level Address Translation (SLAT) and Input-Output Memory Management Unit (IOMMU).
  • Credential dumping tools cannot communicate directly with LsaIso.exe, rendering automated dumping attacks ineffective.

Hardware Dependencies

Credential Guard relies on specific hardware features to maintain its security boundary:

  • A 64-bit CPU supporting virtualization extensions (Intel VT-x or AMD-V) and SLAT.
  • UEFI firmware running in native mode with Secure Boot enabled to ensure the hypervisor boots in a verified, uncompromised state.
  • A Trusted Platform Module (TPM) to bind the virtualization keys securely to the physical hardware.
