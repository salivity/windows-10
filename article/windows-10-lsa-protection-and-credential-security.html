Windows 10 LSA Protection and Credential Security

The Local Security Authority (LSA) protection mode in Windows 10 is a critical defense mechanism designed to prevent unauthorized access to sensitive authentication data stored in system memory. By running the Local Security Authority Subsystem Service (LSASS) as a Protected Process Light (PPL), Windows restricts non-protected processes from reading its memory space or injecting malicious code. This article examines the function of LSA protection mode, the specific threats it mitigates, how it isolates LSASS, and why it is essential for enterprise credential defense.

Understanding the Local Security Authority Subsystem Service (LSASS)

The Local Security Authority Subsystem Service runs as lsass.exe and is responsible for enforcing security policies, managing user authentication, issuing security tokens, and handling password changes. To authenticate users and facilitate Single Sign-On (SSO) across networks, LSASS temporarily stores active credentials in memory. These credentials can include plaintext passwords, Kerberos tickets, and NTLM password hashes.

Because lsass.exe centralizes this sensitive data, it is a primary target for attackers seeking to move laterally across an enterprise network.

The Attack Vector: Credential Dumping

Without enhanced protections, an attacker who obtains local administrative privileges can access the memory space of lsass.exe. Using tools like Mimikatz or built-in utilities like Task Manager and procdump, attackers can extract credential materials directly from memory. Once these hashes or Kerberos tickets are dumped, adversaries execute Pass-the-Hash or Pass-the-Ticket attacks, granting them access to other resources on the network without needing the user's actual password.

How LSA Protection Mode Guards Credentials

Introduced as a built-in feature and expanded in Windows 8.1 and Windows 10, LSA protection enforces the Protected Process Light (PPL) model on lsass.exe. This process isolation mechanism plays several key security roles:

  • Memory Access Restriction: Even if an attacker achieves administrative or SYSTEM-level privileges, the operating system prevents non-protected processes from using API calls—such as OpenProcess with PROCESS_VM_READ or PROCESS_ALL_ACCESS rights—against the LSASS process. This blocks external utilities from reading LSASS memory directly.
  • Code Injection Prevention: Attackers often try to inject dynamic link libraries (DLLs) or shellcode into lsass.exe to intercept credentials as they are processed. LSA protection prevents threads from being created in LSASS by outside processes, stopping arbitrary code injection.
  • Mandatory Digital Signatures: Under LSA protection, any plug-in, security support provider (SSP), or driver loaded by LSASS must be digitally signed with a verified Microsoft signature. Unsigned or third-party binaries that lack proper cryptographic verification are rejected, preventing persistence via malicious SSPs.

Deployment and Configuration

In Windows 10, LSA protection can be enabled via Group Policy or by configuring the Windows Registry:

  1. Registry Key: HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Lsa
  2. Value Name: RunAsPPL
  3. Value Data: Setting this DWORD value to 1 enforces PPL mode, requiring a system reboot to take effect.

Before enabling LSA protection across an environment, organizations typically run it in audit mode (event tracking) to verify that legacy or third-party authentication software does not attempt to load unsigned modules into LSASS, which would disrupt standard login workflows.

Relationship with Credential Guard

While LSA protection (PPL) hardens the lsass.exe process within the operating system, Windows 10 also offers Windows Defender Credential Guard, which uses Virtualization-Based Security (VBS) to isolate credential secrets inside a virtualized container entirely separate from the host OS kernel. LSA protection serves as a strong, software-level baseline of defense that does not strictly require hardware virtualization, making it broadly deployable while drastically increasing the difficulty of credential theft.
