How Windows 10 Isolates Low-Integrity Processes

Microsoft Windows 10 secures the operating system against malicious code through Mandatory Integrity Control (MIC), an authorization mechanism that restricts the access permissions of applications running at lower trust levels. By categorizing processes and securable objects into hierarchical Integrity Levels (ILs), Windows enforces the principle of least privilege, preventing untrusted or compromised software—such as sandboxed web browsers—from altering files, registry settings, or memory belonging to higher-integrity components.

Integrity Levels in Windows 10

Windows 10 assigns an Integrity Level to every security principal (processes, users) and securable object (files, registry keys, synchronization handles). The primary levels, from lowest to highest, include:

  • Untrusted: Reserved for processes with virtually no rights (e.g., anonymous sessions).
  • Low: Used for sandboxed applications, restricted network-facing software, and isolated web browser tabs.
  • Medium: The standard level for non-elevated user applications.
  • High: Assigned to elevated processes running with full administrative rights via User Account Control (UAC).
  • System: Reserved for the operating system kernel, services, and core system functions.

The "No-Write-Up" Policy

The core foundation of MIC process isolation is the "No-Write-Up" (NWU) enforcement rule. While traditional Discretionary Access Control Lists (DACLs) grant permissions based on user identity, MIC adds a mandatory layer defined in the object's System Access Control List (SACL) via a mandatory label.

Under this policy:

  • A low-integrity process can read objects at a Medium or High level if the DACL allows read access ("Read-Up" is generally permitted).
  • A low-integrity process cannot obtain write, delete, or append access to any object with a higher integrity level, regardless of DACL permissions ("No-Write-Up").

If an attacker compromises a low-integrity application, the operating system kernel prevents the payload from writing to system directories, modifying the user's startup registry keys, or tampering with files created by standard user processes.

Memory and Process Handle Isolation

To prevent process injection attacks, Windows 10 restricts how low-integrity processes interact with other running processes in memory.

When a process attempts to open a handle to another process using the OpenProcess API, the kernel checks the caller's integrity level against the target's integrity level. A low-integrity process is denied access rights such as PROCESS_VM_WRITE, PROCESS_VM_OPERATION, and PROCESS_CREATE_THREAD against Medium, High, or System processes. This mitigates techniques such as DLL injection, thread hijacking, and code injection from sandboxed environments.

User Interface Privilege Isolation (UIPI)

Windows 10 implements User Interface Privilege Isolation (UIPI) to prevent attacks through the Windows messaging subsystem. Without UIPI, a low-integrity process could send malicious Windows messages (such as WM_COMMAND or WM_DROPFILES) to higher-integrity windows to execute code with elevated privileges.

UIPI blocks low-integrity processes from:

  • Sending window messages to higher-integrity windows using SendMessage or PostMessage.
  • Using thread hooks on higher-integrity processes.
  • Querying the properties or status of higher-integrity UI elements.

Storage and Registry Sandboxing

Low-integrity processes are constrained to dedicated storage and registry locations configured specifically for low-trust operations.

  • File System: Low-integrity applications are restricted to designated low-integrity folders (such as subfolders within AppData\Local\Packages or designated temporary internet folders). Attempts to write outside these folders are blocked with an access-denied error.
  • Registry: Low-integrity processes can only write to specific registry hives configured with a Low Mandatory Label, primarily under isolated subkeys within HKEY_CURRENT_USER\Software\AppDataLow. Critical configurations in HKEY_LOCAL_MACHINE and standard HKEY_CURRENT_USER paths remain inaccessible for modification.
