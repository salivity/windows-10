UEFI Secure Boot in Windows 10 Explained

This article explains how the Microsoft Windows 10 operating system implements Secure Boot verification via UEFI (Unified Extensible Firmware Interface) firmware. Secure Boot is a security standard designed to ensure that a device boots using only software that is trusted by the Original Equipment Manufacturer (OEM). By establishing a cryptographically validated chain of trust—from the initial hardware power-on through the execution of the Windows kernel and early drivers—Windows 10 protects systems against low-level threats such as bootkits and rootkits.

The Foundation: UEFI Databases and the Chain of Trust

Secure Boot operates using a Public Key Infrastructure (PKI) embedded directly into the motherboard's non-volatile firmware storage (NVRAM). This structure relies on four primary databases:

  • Platform Key (PK): Establishes the relationship between the platform owner and the firmware.
  • Key Exchange Key (KEK): Authorizes operating system vendors (like Microsoft) to update the signature databases.
  • Authorized Signature Database (db): Contains the public keys, certificates, and cryptographic hashes of approved firmware components, bootloaders, and operating system kernels.
  • Forbidden Signature Database (dbx): Contains revocation lists of malicious or compromised keys and binary hashes, preventing previously signed but vulnerable software from executing.

Step 1: Firmware Verification of the Windows Boot Manager

When a Windows 10 PC powers on, the UEFI platform firmware initializes the hardware and attempts to launch the operating system. Instead of executing arbitrary code from a master boot record, the firmware locates the Windows EFI system partition and finds the Windows Boot Manager executable (bootmgfw.efi).

Before execution, the UEFI firmware calculates the cryptographic hash of bootmgfw.efi and verifies its signature against the certificates in the authorized database (db). Typically, this file is signed by the "Microsoft Corporation UEFI CA." If the file has been modified, lacks a valid signature, or matches an entry in the forbidden database (dbx), the firmware halts execution immediately and refuses to boot.

Step 2: Bootloader Verification of the Windows OS Loader

Once verified, execution passes to bootmgfw.efi. The Windows Boot Manager assumes responsibility for the chain of trust. It checks the integrity of its configuration settings in the Boot Configuration Data (BCD) store and locates the Windows OS Loader (winload.efi).

bootmgfw.efi verifies the digital signature of winload.efi against Microsoft's embedded release signing certificates. If the signature is valid and untampered, control transitions to winload.efi.

Step 3: Loading the Kernel and Hardware Abstraction Layer

The Windows OS Loader (winload.efi) takes over the task of loading the core Windows operating system components into memory:

  1. The Windows Kernel (ntoskrnl.exe)
  2. Hardware Abstraction Layer (hal.dll)
  3. Boot-start Drivers and the Early Launch Anti-Malware (ELAM) driver

Every file loaded by winload.efi must be signed with a trusted Microsoft Production Code Signing Certificate. If any file fails verification, Windows aborts the boot process and triggers the Windows Recovery Environment (WinRE).

Step 4: Early Launch Anti-Malware (ELAM) and Driver Initialization

Before initializing regular third-party boot drivers, winload.efi launches the registered ELAM driver. Because ELAM starts before any other driver, it inspects every subsequent driver scheduled to load during initialization.

The ELAM driver classifies each driver as known good, known bad, or unclassified. The Windows kernel then uses this classification to determine whether to initialize the driver or block it, preventing boot-time rootkits from compromising the operating system before traditional anti-malware services can start.

Once ELAM and the necessary boot drivers pass verification, the Windows kernel finishes initialization and transitions the system into user mode, completing a fully verified, tamper-resistant boot process.
