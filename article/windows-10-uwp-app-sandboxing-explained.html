Windows 10 UWP App Sandboxing Explained

Universal Windows Platform (UWP) applications distributed through the Microsoft Store run inside a tightly controlled execution environment designed to protect the operating system and user data from malicious behavior. Windows 10 achieves this sandboxing through a multi-layered security architecture anchored by the AppContainer execution environment, declarative permission models, file and registry virtualization, and brokered access to sensitive system resources.

The AppContainer Security Boundary

At the core of UWP sandboxing is the AppContainer, a specialized, low-integrity security context built into the Windows NT kernel. When a UWP app launches, the Windows security subsystem generates a unique Security Identifier (SID) for the application package.

Unlike standard Win32 applications, which typically inherit the full access token and privileges of the signed-in user, an AppContainer operates with restricted tokens. The operating system attaches a mandatory integrity label set to "Low." This ensures the app cannot interact with or inject code into standard user-level processes (which run at "Medium" integrity) or administrative processes (which run at "High" integrity).

Declared Capabilities and the App Manifest

UWP applications adhere to the principle of least privilege. An application cannot access hardware or system resources by default; access must be explicitly defined in the application's package manifest (Package.appxmanifest).

Windows 10 categorizes permissions into distinct tiers:

  • Standard Capabilities: Basic functionalities, such as outgoing internet access (internetClient), which are automatically granted during installation.
  • Device Capabilities: Access to peripheral hardware, including webcams, microphones, location sensors, and Bluetooth radios. Windows requires explicit user consent via runtime prompts before granting access to these APIs.
  • Restricted Capabilities: Advanced system functions (such as full file system access or background media processing) that require verification by Microsoft before an application can be published to the Store.

If an application attempts to invoke an API for an undeclared capability, the Windows runtime immediately blocks the call.

File System and Registry Virtualization

UWP applications cannot freely browse the broader Windows file system or system registry. Instead, the OS confines each app to an isolated data compartment:

  • App-Specific Storage: Each app receives private storage partitions located under %LOCALAPPDATA%\Packages\[PackageFamilyName]\. Inside this space, the app can read and write to dedicated LocalState, RoamingState, and TempState directories. Other applications cannot access these folders.
  • Registry Isolation: UWP apps do not write to the global Windows Registry hives (HKEY_LOCAL_MACHINE or standard HKEY_CURRENT_USER). Instead, registry writes are redirected to private, per-package hive files (User.dat), preventing system-wide configuration tampering.
  • Read-Only App Directory: The app’s installation directory (under C:\Program Files\WindowsApps) is read-only and secured by Access Control Lists (ACLs) managed by the OS, preventing tampering with executable binaries.

Brokered Access via Runtime Broker

When a sandboxed application needs to interact with files or services outside its sandbox, it must use brokered Windows Runtime (WinRT) APIs.

Windows 10 delegates these requests to a background system process called RuntimeBroker.exe. For instance, if an app needs to open a file from the user's Documents folder:

  1. The app invokes the FileOpenPicker API.
  2. The user sees a standard Windows file-selection dialog managed entirely outside the app's process space by the OS.
  3. Once the user explicitly selects a file, the OS grants the app temporary, targeted read or write permissions only to that specific file object. The app never gains access to the parent folder.

Network Isolation

Windows 10 enforces network-level sandboxing through Windows Filtering Platform (WFP) rules specifically mapped to the app's package SID:

  • Inbound Block: Inbound network connections are blocked by default unless explicitly declared.
  • Network Segmentation: Home/work (private) networks and public internet networks require distinct, independent capability declarations (privateNetworkClientServer vs. internetClient).
  • Loopback Restrictions: To prevent local inter-process communication attacks, UWP applications are blocked from sending network traffic to localhost (127.0.0.1) by default, isolating them from other locally running servers and services.
