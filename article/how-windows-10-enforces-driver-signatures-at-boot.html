How Windows 10 Enforces Driver Signatures at Boot

Driver Signature Enforcement (DSE) in Microsoft Windows 10 is a critical security architecture designed to prevent unsigned, tampered, or malicious code from executing within the high-privilege kernel space. This article details the sequential boot-time mechanisms Windows 10 uses to validate drivers, covering the chain of trust established from the UEFI firmware up through the Windows Boot Loader, Code Integrity subsystem, and modern hardware-isolated security layers.

The Hardware Chain of Trust: UEFI Secure Boot

The enforcement process begins before the operating system even starts executing. In modern systems running Windows 10, UEFI Secure Boot establishes a hardware-backed root of trust:

  1. Firmware Verification: The motherboard firmware reads its non-volatile memory (containing the Signature Database db and Forbidden Database dbx) to verify the digital signature of the Windows Boot Manager (bootmgr.efi).
  2. Handoff: If the cryptographic signature is verified against a trusted Microsoft certificate stored in the firmware, execution is handed to bootmgr.efi. If verification fails, the boot process halts immediately.

Boot-Start Driver Validation via winload.efi

The Windows Boot Manager locates the active BCD (Boot Configuration Data) store and loads the Windows Operating System Loader (winload.efi). The OS Loader is responsible for loading the kernel and the initial set of boot-start drivers (drivers marked with a START type of SERVICE_BOOT_START):

  • Self-Integrity Check: winload.efi ensures its own binary signature is valid and unmodified.
  • Loading Boot Binaries: winload.efi reads the core Windows kernel (ntoskrnl.exe), the Hardware Abstraction Layer (hal.dll), and critical storage and system boot drivers from disk into memory.
  • Pre-Execution Signature Check: Before these files are executed or handed to the kernel, winload.efi checks their embedded signatures or corresponding catalog (.cat) files. The loader verifies the cryptographic hashes (typically SHA-256) and confirms that the signing certificate chains up to a trusted Microsoft Root Authority.
  • Boot Abort: If a boot-start driver lacks a valid signature or has been tampered with, winload.efi refuses to pass control to the operating system, triggering a blue screen or recovery environment with an error such as 0xc0000428 (Windows cannot verify the digital signature for this file).

Kernel-Mode Code Signing (KMCS) and ci.dll

Once winload.efi successfully verifies the essential boot files, it transfers execution to ntoskrnl.exe. From this point, the Code Integrity library (ci.dll) manages and enforces signature policies for the remainder of the operating system's lifecycle:

  • Policy Initialization: ci.dll initializes kernel-mode code signing policies based on system configuration and Windows version requirements (such as requiring drivers to be signed through the Microsoft Windows Hardware Dev Center dashboard).
  • Driver Entry Interception: Whenever a driver service attempts to load (via NtLoadDriver or the Plug and Play manager), the kernel invokes Code Integrity validation routines.
  • Certificate Chain Validation: The driver's Authenticode signature is inspected to ensure it contains an authorized cross-certificate or a direct Microsoft WHQL (Windows Hardware Quality Labs) / Attestation signature.
  • Revocation Checking: The driver's certificate is cross-referenced with revocation lists to ensure the signing key has not been revoked or compromised.

Protection via Hypervisor-Protected Code Integrity (HVCI)

In legacy architectures, attackers with temporary kernel execution could bypass DSE by modifying the global kernel variable responsible for validation (such as patching g_CiOptions in memory to disable verification).

Windows 10 mitigates this by utilizing Virtualization-Based Security (VBS) and Hypervisor-Protected Code Integrity (HVCI):

  • Isolated Memory: HVCI runs the Code Integrity module inside an isolated virtual environment (Virtual Secure Mode, or VSM) managed by the Hyper-V hypervisor, completely segregated from the standard kernel (VTL0).
  • Hardware Enforcement: The hypervisor controls Second Level Address Translation (SLAT) page tables. Even if an attacker achieves ring 0 (kernel) execution, they cannot write to executable memory or alter the signing policies hosted in VTL1.
  • Strict Execution Control: A driver page cannot be mapped as both writable and executable (W^X policy). The hypervisor only grants execution rights to a page after the isolated Code Integrity module in VTL1 has verified the driver’s cryptographic signature.
