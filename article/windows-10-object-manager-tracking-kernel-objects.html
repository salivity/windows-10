Windows 10 Object Manager: Tracking Kernel Objects

The Windows 10 Object Manager is a foundational component of the Windows NT executive subsystem responsible for creating, maintaining, securing, and destroying kernel-level objects. By serving as a unified resource manager, it abstracts physical and logical system entities—such as processes, threads, files, and synchronization primitives—into standardized structures. This article examines the architectural role of the Object Manager in tracking these kernel objects, detailing how it maintains object lifecycles, manages system namespaces, enforces access control, and uses reference counting to guarantee operating system integrity and stability.

Centralized Object Creation and Standardization

In Windows 10, kernel-level resources are represented as structured objects rather than raw blocks of memory. The Object Manager (Ob) standardizes these entities by splitting each object into two parts: a standard object header and an object-specific body.

The object header, managed exclusively by the Object Manager, contains system-wide metadata such as the object’s name, security descriptor, quota charges, and type information. The object body is defined and manipulated by the specific executive component that owns the object (for example, the Process Manager for process objects or the Memory Manager for section objects). By standardizing the header, the Object Manager tracks all kernel components using a uniform interface, eliminating the need for individual subsystems to implement proprietary tracking logic.

Reference Counting and Lifetime Management

One of the most critical roles of the Object Manager is tracking the lifecycle of kernel objects to prevent memory leaks and dangling pointers. It accomplishes this using a dual-counter mechanism stored in the object header:

  • Pointer Count: Tracks the number of active kernel-mode references to the object. Every time an internal driver or kernel subsystem retains a pointer to an object, the pointer count increments.
  • Handle Count: Tracks the number of user-mode or kernel-mode handles open to the object. When a process opens an object via an API call, a handle is generated in that process's handle table, incrementing the handle count (and, by extension, the pointer count).

The Object Manager ensures that an object remains in memory as long as its pointer count is greater than zero. When all handles are closed, the handle count drops to zero, allowing the system to perform pre-deletion cleanup, such as removing the object’s name from the namespace. Once all kernel-mode pointer references are released and the pointer count reaches zero, the Object Manager permanently deallocates the object's memory from the non-paged or paged pool.

Unified Namespace Management

The Object Manager maintains a hierarchical, directory-based namespace—similar to a file system—that organizes named kernel objects. This internal structure is distinct from the physical file system and can be inspected using diagnostic tools like WinObj.

By categorizing objects under directories such as \Device, \Driver, \KernelObjects, and \BaseNamedObjects, the Object Manager enables inter-process communication and object sharing. When a process requests access to a named object, the Object Manager traverses this namespace, parses the path, and resolves symbolic links to locate or create the requested resource.

Security Integration and Access Control

Tracking kernel objects also requires governing which entities can interact with them. The Object Manager integrates directly with the Security Reference Monitor (SRM) to enforce access validation.

When an application attempts to access an object, the Object Manager intercepts the request and evaluates the caller’s access token against the discretionary access control list (DACL) stored in the object's header. If the request is permitted, the Object Manager creates an entry in the calling process's handle table and grants a specific access mask (such as read, write, or execute). Subsequent operations using that handle avoid repeated, costly security checks because the granted rights are bound directly to the handle tracked by the Object Manager.
