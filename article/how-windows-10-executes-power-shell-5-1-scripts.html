How Windows 10 Executes PowerShell 5.1 Scripts

When Windows 10 runs a Windows PowerShell 5.1 script, it initiates a multi-stage process that involves starting a host process, verifying system security controls, parsing the script text, and executing instructions through the .NET Framework. This article breaks down the internal sequence of events Windows 10 uses to process, inspect, and run PowerShell .ps1 files from initiation to completion.

Process Initialization

The execution begins when a user or automated task invokes powershell.exe. Windows creates a new process for the console host, which hosts the PowerShell engine implemented in the System.Management.Automation.dll assembly. Because PowerShell 5.1 is built on the .NET Framework, the host process immediately bootstraps the Common Language Runtime (CLR) version 4.0. The CLR manages memory, garbage collection, and low-level system interactions throughout the script's lifecycle.

Execution Policy Verification

Before reading or running a script file, PowerShell checks the current Execution Policy. Windows 10 sets the default policy to Restricted, which prevents all .ps1 files from running. If configured to policies like RemoteSigned or AllSigned, the engine verifies the script's digital signature and its zone of origin using Windows Alternate Data Streams (specifically, the Zone.Identifier). If the policy prevents execution, the engine throws an error and terminates before any code runs.

Antimalware Scan Interface (AMSI) Inspection

To guard against malicious code, Windows 10 routes the raw script content through the Antimalware Scan Interface (AMSI). AMSI delivers the plain text of the script—as well as any de-obfuscated or dynamically generated code—directly to the installed antivirus solution (such as Microsoft Defender) before parsing occurs. If the security provider determines the content is malicious, PowerShell aborts execution and denies access.

Parsing and Abstract Syntax Tree (AST) Generation

Once cleared by security filters, the PowerShell engine's parser processes the script text:

  1. Tokenization: The lexical analyzer splits the code into discrete tokens, identifying keywords, variables, operators, and strings.
  2. AST Construction: The parser arranges tokens into an Abstract Syntax Tree (AST), creating a structured, hierarchical model of the script logic.
  3. Semantic Analysis: The engine evaluates variable scopes, parameter declarations, and command validity.

Dynamic Compilation and Pipeline Execution

PowerShell 5.1 relies on the Dynamic Language Runtime (DLR) to translate the AST into executable bytecode. The engine compiles language constructs (such as loops and conditions) into dynamic expression trees, which the CLR compiles into native machine code at runtime using Just-In-Time (JIT) compilation.

The commands are then executed sequentially within the PowerShell pipeline:

  • Cmdlets and Functions: Native cmdlets run inside the host process as compiled .NET classes derived from Cmdlet or PSCmdlet.
  • External Executables: Non-PowerShell commands (such as cmd.exe or ipconfig.exe) are launched as child processes via the standard Windows Win32 CreateProcess API, with their standard input, output, and error streams piped back into the PowerShell host.

Cleanup and Termination

After the last statement in the script finishes executing, the PowerShell engine clears local variables, releases handles to files or system resources, and returns an exit code (typically stored in $LASTEXITCODE) to the operating system before the host process either returns to an interactive prompt or closes entirely.
