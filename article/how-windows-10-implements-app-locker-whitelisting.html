How Windows 10 Implements AppLocker Whitelisting

Microsoft Windows 10 implements application whitelisting through AppLocker, a native security framework designed to restrict unauthorized software, scripts, and installers from executing. Available in Windows 10 Enterprise and Education editions, AppLocker enforces administrative policies by intercepting execution requests at the kernel level, evaluating file properties against a predefined set of allow rules, and either permitting or denying process launch.

Core Components and Execution Mechanism

AppLocker relies on two fundamental operating system components to identify and evaluate binaries:

  1. Application Identity Service (AppIDSvc): This background service extracts metadata from target files—such as digital signatures, product names, versions, and file hashes—required to match files against configured policies. The service must be set to run automatically for AppLocker enforcement to function.
  2. AppLocker Kernel Driver (appid.sys): Windows 10 intercepts process creation using kernel-level process creation callbacks (PsSetCreateProcessNotifyRoutineEx). When a user attempts to execute a file, appid.sys intercepts the call and queries the policy cache. If the binary matches an "Allow" rule, the process is allowed to spawn; if it matches a "Deny" rule or fails to match any allow rule, execution is blocked.

Rule Collections

AppLocker categorizes executables into distinct rule collections to manage different execution environments across the system:

  • Executable Rules: Controls standard binary execution, including .exe and .com files.
  • Windows Installer Rules: Regulates installation packages such as .msi, .msp, and .mst files.
  • Script Rules: Restricts script execution across interpreters, covering PowerShell (.ps1), batch files (.bat, .cmd), VBScript (.vbs), and JScript (.js).
  • Packaged App Rules: Governs Universal Windows Platform (UWP) apps and packaged store apps (.appx).
  • DLL Rules: Controls dynamic link libraries (.dll and .ocx). This collection is disabled by default due to high performance overhead, as every loaded module must be evaluated.

Rule Condition Types

Administrators configure AppLocker by specifying one of three primary condition types to determine whether an application is permitted:

  • Publisher Conditions: Leverages cryptographic digital signatures. Rules can permit all software signed by a specific vendor (e.g., Microsoft or a trusted internal certificate authority) or scope rules down to specific product names, file names, or minimum versions. This is the recommended condition because it survives software updates without administrative overhead.
  • Path Conditions: Evaluates the directory location of a file. While easy to implement, path rules require strict Access Control Lists (ACLs) to ensure non-administrative users cannot write to or modify files within approved directories.
  • File Hash Conditions: Generates an SHA-256 authenticode hash of the binary. This method strictly ensures file integrity; however, hashes change with every software patch or update, requiring administrators to regenerate rules frequently.

Enforcement and Auditing

AppLocker supports two operational modes:

  • Enforce Rules: All unapproved execution requests are blocked immediately, presenting the user with an access-denied error dialog.
  • Audit Only: Applications execute normally, but any execution that would have been blocked under an active policy is logged. All events are recorded in the Windows Event Viewer under Applications and Services Logs > Microsoft > Windows > AppLocker.

Management and Deployment

AppLocker policies are centrally defined and distributed using Group Policy Objects (GPOs) through secpol.msc or Active Directory domain controllers. The policy structure is stored as an XML configuration under Computer Configuration > Windows Settings > Security Settings > Application Control Policies > AppLocker. Once updated, Windows 10 applies the policy locally via Group Policy client processing, directly updating the local registry under HKLM\SOFTWARE\Policies\Microsoft\Windows\SrpV2 to feed the appid.sys kernel driver.
