Windows 10 TLS 1.2 and TLS 1.3 Handshake Management

This article examines how the Microsoft Windows 10 operating system processes Transport Layer Security (TLS) 1.2 and TLS 1.3 cryptographic handshakes. It outlines the role of the Secure Channel (Schannel) Security Support Provider, the internal mechanics of key exchange and cipher negotiation for both protocol versions, and how Windows 10 optimizes, configures, and secures network communications across modern enterprise environments.

The Role of Schannel in Windows 10

Windows 10 delegates all native TLS operations to the Secure Channel Security Support Provider (Schannel.dll), which interfaces through the Security Support Provider Interface (SSPI) and utilizes Cryptography Next Generation (CNG) cryptographic primitives. When an application, such as Microsoft Edge or an enterprise service, initiates an HTTPS connection, it calls Schannel to establish the secure channel. Schannel inspects the system's cryptographic policies, available cipher suites, and registry configurations to determine which protocol version and parameters to propose during the handshake.

The TLS 1.2 Handshake Process in Windows 10

In Windows 10, TLS 1.2 follows a standard two-round-trip time (2-RTT) negotiation model:

  1. Client Hello: Schannel initiates the connection by transmitting supported protocol versions, a random nonce, session ID, supported compression methods, and an ordered list of enabled cipher suites determined by Windows Group Policy or local registry configurations.
  2. Server Response: The remote server responds with a ServerHello selecting the cipher suite, provides its digital certificate chain for validation, sends a ServerKeyExchange message containing its ephemeral Diffie-Hellman parameters (if ECDHE/DHE is used), and concludes with a ServerHelloDone.
  3. Key Exchange and Verification: Windows 10 verifies the server's certificate against its local Trusted Root Certification Authorities store via the CryptoAPI (CAPI2). Upon verification, the client generates its key exchange parameters, sends a ClientKeyExchange message, issues a ChangeCipherSpec record, and sends an encrypted Finished message containing a hash of all previous handshake messages.
  4. Completion: The server confirms receipt, responds with its own ChangeCipherSpec and Finished message, and symmetric encryption begins.

The TLS 1.3 Handshake Optimization in Windows 10

Windows 10 introduced support for TLS 1.3 in later feature updates, enabling faster connection establishment and enhanced security by removing obsolete cryptographic algorithms.

TLS 1.3 reduces the handshake to a single round-trip time (1-RTT):

  1. Optimized Client Hello: Schannel guesses the server’s preferred key exchange algorithm (typically Curve25519 or secp256r1) and immediately sends its ephemeral key shares alongside the ClientHello and supported symmetric cipher suites.
  2. Server Key Generation and Flight: The server selects the cryptographic parameters, generates its own key share, and computes the shared secret immediately. It responds with a ServerHello, key share, and encrypted handshake messages (including the server certificate and an encrypted Finished verification).
  3. Immediate Data Transmission: Windows 10 computes the shared secret using the server's key share, validates the encrypted certificate chain, verifies the handshake integrity, and responds with its Finished message. Application data can be transmitted immediately after this single round trip.

Additionally, Windows 10 supports Zero Round-Trip Time (0-RTT) resumption in TLS 1.3, allowing previously connected clients to send encrypted application data in the initial flight using pre-shared keys (PSK), provided the application layer permits early data.

Cipher Suite Negotiation and Protocol Selection

Windows 10 determines handshake parameters strictly based on local priority lists. Schannel filters out deprecated primitives—such as RC4, 3DES, MD5, and static RSA key exchanges—when negotiating TLS 1.3, relying exclusively on Authenticated Encryption with Associated Data (AEAD) algorithms (such as AES-GCM and ChaCha20-Poly1305).

System administrators control how Windows 10 manages these handshakes through:

  • The Windows Registry: Protocol versions are enabled or disabled under HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\.
  • Group Policy: Cipher suite ordering is customized under Computer Configuration > Administrative Templates > Network > SSL Configuration Settings, enforcing which cryptographic algorithms Schannel presents during the initial ClientHello.
