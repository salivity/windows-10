Windows 10 Kernel-Mode Driver Code Signing

This article examines how the Microsoft Windows 10 operating system enforces code signing on kernel-mode drivers to protect the core operating system from unauthorized or malicious execution. It outlines the core architecture of Driver Signature Enforcement (DSE), the mandatory requirement for Microsoft-attested signatures via the Hardware Dev Center, and the hardware-backed security features like Secure Boot and Hypervisor-Protected Code Integrity (HVCI) that prevent these security checks from being bypassed.

The Purpose of Kernel-Mode Code Signing

Kernel mode operates at Ring 0, the highest privilege level in the processor architecture. Any code executing in kernel mode has direct access to system memory, hardware components, and critical OS structures. A flaw or malicious payload at this level can bypass standard user-mode security boundaries, install stealth rootkits, or cause catastrophic system crashes (Blue Screens of Death).

To mitigate these risks, Windows 10 strictly enforces Kernel-Mode Code Signing (KMCS) to guarantee two critical properties before a driver runs: identity (authenticity of the developer) and integrity (ensuring the code has not been altered since it was signed).

Driver Signature Enforcement (DSE)

The primary enforcement engine within Windows 10 is Driver Signature Enforcement (DSE), integrated directly into the NT kernel (ntoskrnl.exe) and the Code Integrity module (ci.dll).

When a driver loading request is initiated (such as via the ZwLoadDriver system call), the kernel suspends the load process to perform cryptographic verification:

  1. Header Inspection: The system reads the driver's Portable Executable (PE) headers to locate the embedded Authenticode signature or checks the driver against a signed security catalog (.cat) file.
  2. Hash Validation: The system calculates the cryptographic hash (SHA-256) of the driver image and compares it to the hash signed inside the certificate. Any discrepancy halts the load immediately.
  3. Chain of Trust: The driver's signing certificate is traced up to a trusted root authority stored in the operating system's protected certificate store.

If a driver lacks a valid signature, has an expired certificate, contains an untrusted root, or fails hash verification, Windows 10 refuses to load the binary into memory and logs a CodeIntegrity event in the Event Viewer (Event ID 3004).

The Microsoft Portal Signing Mandate

Starting with Windows 10, version 1607, Microsoft significantly tightened kernel signing policies. Traditional third-party cross-signing—where developers used standard Authenticode certificates issued by public Certificate Authorities (CAs) to self-sign drivers—was deprecated.

For Windows 10:

  • Hardware Dev Center Dashboard: All new kernel-mode drivers must be submitted to the Microsoft Partner Center.
  • Extended Validation (EV) Requirement: Developers must use an Extended Validation (EV) code signing certificate to establish a developer account and submit packages.
  • Microsoft Signature: After automated testing via the Windows Hardware Lab Kit (HLK) or attestation signing, Microsoft signs the final driver package with the official Microsoft Windows Hardware Compatibility Program (WHQL) signature.

Drivers lacking this specific Microsoft-signed counter-signature will not load on fresh installations of Windows 10 with Secure Boot enabled.

Secure Boot and the Boot Process

Code signing enforcement begins before Windows 10 even finishes booting. The Unified Extensible Firmware Interface (UEFI) Secure Boot protocol establishes a hardware-based root of trust:

  1. The platform firmware verifies the digital signature of the Windows Boot Manager (bootmgfw.efi).
  2. The Boot Manager verifies the Windows OS Loader (winload.efi).
  3. winload.efi verifies the kernel (ntoskrnl.exe), the Code Integrity library, and Boot-Start drivers, including Early Launch Anti-Malware (ELAM) drivers.
  4. Once the kernel initializes, it inherits this chain of trust and maintains DSE for all subsequent on-demand driver loads.

If Secure Boot is enabled, system policies strictly disallow test-signed drivers and disable the legacy debugging modes that would otherwise bypass DSE.

Virtualization-Based Security (VBS) and HVCI

To defend against advanced threats that attempt to disable DSE in memory (such as exploiting write-what-where vulnerabilities to flip the g_CiOptions kernel variable to disable verification), Windows 10 uses Virtualization-Based Security (VBS) and Hypervisor-Protected Code Integrity (HVCI).

HVCI shifts the enforcement of code integrity from the standard kernel to a secure, isolated environment powered by the Windows Hypervisor:

  • The system is split into Virtual Trust Levels: VTL 0 (normal OS and kernel) and VTL 1 (isolated, secure environment).
  • In this configuration, Code Integrity checks run inside VTL 1.
  • The hypervisor enforces Second Level Address Translation (SLAT) permissions, designating memory pages as either Writable or Executable, but never both simultaneously (W^X).
  • Before a page in kernel memory can become executable, VTL 1 validates its digital signature.

Because the code integrity state is isolated inside VTL 1, a compromised VTL 0 kernel cannot manipulate kernel memory to bypass driver signing checks.
