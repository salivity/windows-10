How Windows 10 BitLocker Uses TPM PCR Registers

This article provides an overview of how the Microsoft Windows 10 operating system secures disk encryption keys using a Trusted Platform Module (TPM). It explains the role of Platform Configuration Registers (PCRs), details the step-by-step cryptographic measurement process during the boot sequence, and describes how BitLocker "seals" and "unseals" keys to ensure data is accessible only when the system boots into a trusted, unaltered state.

The Role of the TPM and PCR Registers

Windows 10 implements full-volume disk encryption through BitLocker, which relies on a hardware TPM chip to store and protect encryption keys. The TPM contains Platform Configuration Registers (PCRs)—specialized, volatile memory registers designed to hold cryptographic hashes representing the integrity of the system's firmware, hardware configuration, and boot components.

PCRs cannot be directly overwritten with arbitrary data. Instead, they are updated through an operation known as "extending." When a component is measured, the TPM calculates a new hash by combining the existing register value with the hash of the new component:

\[\text{PCR}_{\text{new}} = \text{Hash}(\text{PCR}_{\text{current}} \parallel \text{Measurement})\]

Because each measurement depends on all previous measurements, the final PCR value reflects the exact boot history of the device.

The Measurement Sequence

During startup, the system establishes a Static Root of Trust for Measurement (SRTM). Each component cryptographically measures the subsequent component before executing it:

  1. Firmware Initialization: The Core Root of Trust for Measurement (CRTM) executes and measures the UEFI/BIOS code, storing the result in PCR 0.
  2. Platform Configuration: Extended firmware configuration and motherboard settings are measured into PCR 1.
  3. Option ROMs and Drivers: Third-party drivers and Option ROMs are measured into PCR 2 and PCR 3.
  4. Boot Loader: The Master Boot Record (MBR) or UEFI boot manager is measured into PCR 4.
  5. GPT Partition Table: Disk partitioning information is measured into PCR 5.
  6. Secure Boot and State: Windows 10 heavily relies on PCR 7 to validate that Secure Boot is enabled and that certificates match the authorized database (db/dbx).
  7. Windows Boot Manager and Kernel: The Windows Boot Manager (bootmgr) measures the Windows OS loader (winload.efi) and core boot drivers into PCR 11.

Sealing the Volume Master Key

BitLocker encrypts the volume using a Full Volume Encryption Key (FVEK), which is encrypted by a Volume Master Key (VMK). To enforce system integrity, the VMK is "sealed" to the TPM.

Sealing is a TPM operation where data is encrypted using the TPM's internal Storage Root Key (SRK) alongside an authorization policy tied to specific expected PCR values. By default on modern UEFI systems running Windows 10, BitLocker seals the VMK to PCR 7 (Secure Boot state) or a combination such as PCR 0, 2, 4, and 11 on legacy configurations.

Key Enforcement and the Unsealing Process

When Windows 10 boots, the enforcement mechanism executes automatically:

  1. Unseal Request: The Windows Boot Manager requests the TPM to decrypt (unseal) the VMK.
  2. Integrity Validation: The TPM compares the runtime values currently stored in the designated PCRs with the values recorded when the key was sealed.
  3. Execution Decision:
    • Values Match: If the current PCR hashes match the sealed policy, the TPM decrypts the VMK in secure memory and passes it to the boot loader. The drive is decrypted seamlessly, and Windows boots normally.
    • Values Mismatch: If any boot component has changed—such as an altered boot loader, an unauthorized rootkit, modified firmware, or a disabled Secure Boot configuration—the PCR values will not match the sealed condition. The TPM refuses to release the VMK.

When the TPM rejects the unseal request, Windows 10 halts the standard boot sequence and prompts the user for the 48-digit BitLocker Recovery Key, preventing unauthorized access to the encrypted data.
