How Windows 10 Validates Authenticode Signatures

This article provides an overview of how the Microsoft Windows 10 operating system verifies the authenticity and integrity of executable files using Microsoft Authenticode. It examines the step-by-step verification pipeline, covering the extraction of embedded PKCS #7 signatures from Portable Executable (PE) files, cryptographic hash verification, certificate trust chain evaluation, timestamp analysis, and the enforcement of system trust policies via native APIs.

1. Extraction of the Signature from the PE File

Executables in Windows use the Portable Executable (PE) format. Authenticode stores signature data in an area designated as the Attribute Certificate Table.

When Windows 10 evaluates an executable, the operating system inspects the optional header's data directories, specifically locating the IMAGE_DIRECTORY_ENTRY_SECURITY entry. This entry points to a structure containing a standard PKCS #7 / Cryptographic Message Syntax (CMS) digital signature, which wraps the publisher's X.509 certificate, the encrypted hash of the file, and any countersignatures (timestamps).

2. Cryptographic Hash Calculation (Integrity Check)

To ensure the binary has not been tampered with or corrupted, Windows computes a fresh cryptographic digest (typically SHA-256) of the file's contents.

Because embedding the signature alters the file, the hashing algorithm deliberately excludes three specific areas:

  • The file's checksum field in the PE Optional Header.
  • The Certificate Table entry in the Optional Header Data Directories.
  • The Attribute Certificate Table itself (where the signature is embedded).

Windows then decrypts the digest embedded within the PKCS #7 structure using the publisher’s public key and compares it to the newly computed hash. If the hashes match, the integrity of the binary is confirmed.

3. Certificate Chain and Trust Validation

Once file integrity is established, Windows verifies the identity of the software publisher by checking the X.509 certificate chain:

  • Path Building: The OS builds a hierarchical certificate chain starting from the publisher's leaf certificate, continuing through intermediate Certificate Authorities (CAs), and ending at a trusted Root CA.
  • Root Trust Verification: The root certificate must reside in the local system's Trusted Root Certification Authorities store.
  • Validity Period and Constraints: The system verifies that the certificate meets basic constraints, key usage policies (specifically Code Signing, OID 1.3.6.1.5.5.7.3.3), and that the certificate was not expired when the binary was produced.

4. Timestamp Validation (Countersigning)

Certificates naturally expire, but valid software should not immediately become untrusted upon expiration. Authenticode accommodates this using trusted timestamping:

  • When the file was originally signed, a Timestamp Authority (TSA) added an independent, cryptographically signed timestamp (countersignature).
  • Windows 10 checks this timestamp against the publisher's certificate validity period.
  • If the binary was signed while the certificate was active and valid, Windows considers the signature valid indefinitely, even if the primary code-signing certificate has since expired.

5. Revocation Checking

Windows ensures that certificates have not been revoked by the issuing authority due to compromise or misuse:

  • The system queries Certificate Revocation Lists (CRLs) or uses the Online Certificate Status Protocol (OCSP).
  • Windows caches these results locally to minimize performance overhead and network dependency.
  • Additionally, Windows references its internal untrusted certificate store and Microsoft's Disallowed Certificate list to block known malicious certificates immediately.

6. System Policy Enforcement via WinVerifyTrust

The actual verification process is orchestrated programmatically by the WinVerifyTrust function in wintrust.dll, often utilizing the WINTRUST_ACTION_GENERIC_VERIFY_V2 action identifier.

This API synthesizes the results of the integrity, certificate, revocation, and timestamp checks, passing the final trust assessment to user-mode and kernel-mode security subsystems. Based on the result, Windows 10 enforces platform policies such as:

  • User Account Control (UAC): Displays a blue prompt for trusted publishers or an amber prompt for unverified publishers.
  • Windows Defender SmartScreen: Evaluates publisher reputation and blocks unrecognized executables.
  • Driver Signature Enforcement (DSE): Strictly blocks kernel-mode drivers from loading if they do not meet Microsoft's mandatory hardware developer signing requirements.
