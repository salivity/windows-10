Role of SIDs in Windows 10 Access Control Lists

This article examines the critical function of Security Identifiers (SIDs) within the Windows 10 security architecture. It details how the operating system relies on SIDs rather than human-readable names to enforce access permissions, explains how Access Control Lists (ACLs) use these identifiers to grant or deny resource access, and outlines how the Windows Security Reference Monitor evaluates SIDs during user interactions.

In the Microsoft Windows 10 operating system, a Security Identifier (SID) is a unique, immutable value of variable length used to identify a security principal, such as a user account, a security group, or a computer account. SIDs are generated automatically by Windows during the creation of local accounts, or by Active Directory for domain accounts. Once assigned, a SID remains permanently tied to that entity throughout its lifecycle.

Access Control Lists (ACLs) define the permissions assigned to securable objects, such as files, folders, registry keys, and printers. Windows 10 utilizes two types of ACLs: Discretionary Access Control Lists (DACLs), which specify who is granted or denied access to an object, and System Access Control Lists (SACLs), which dictate auditing policies. Within each ACL are individual records called Access Control Entries (ACEs).

The SID serves as the foundational anchor inside every ACE. Rather than binding permissions to usernames or group names, an ACE records the specific SID of the target principal along with the corresponding access mask (such as Read, Write, or Full Control) and an access type (Allow or Deny). By utilizing SIDs within ACEs, Windows separates authorization from mutable account attributes. If an administrator renames a user account or a group, the underlying SID does not change, ensuring that all existing permissions mapped in ACLs remain completely intact and functional without administrative intervention.

The operational role of the SID becomes active during the logon process. When a user authenticates in Windows 10, the Local Security Authority Subsystem Service (LSASS) generates an access token. This token contains the user's primary SID, the SIDs of all security groups the user belongs to, and any associated user privileges.

When the user attempts to access a protected object, the operating system's Security Reference Monitor (SRM) performs an access check. The SRM extracts the SIDs from the user’s access token and compares them against the SIDs contained within the ACEs of the target object's DACL. The SRM evaluates these entries sequentially:

  1. Deny Evaluation: If an ACE explicitly denies access to a SID present in the user's token, access is immediately rejected.
  2. Grant Evaluation: If an ACE grants access to a SID present in the user's token, the requested rights are accumulated until the full request is satisfied.
  3. Implicit Denial: If the SRM reaches the end of the DACL and the user's SIDs have not accumulated all requested permissions, access is blocked by default.

Because the system relies solely on SIDs for this evaluation, deleting an account breaks this relationship. If an account is deleted and a new one is created with the exact same name, it receives a new, distinct SID. As a result, the new account cannot inherit the permissions of the old one, and the previous ACEs appear in the ACL as unresolved, orphaned SIDs. Through this mechanism, SIDs ensure that access control in Windows 10 remains secure, persistent, and unaffected by cosmetic identity changes.
