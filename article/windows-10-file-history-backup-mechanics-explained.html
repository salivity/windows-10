Windows 10 File History Backup Mechanics Explained

Windows 10 File History is a continuous data protection feature designed to safeguard personal files stored in user libraries and desktop folders. This article breaks down the internal mechanics of how File History operates, focusing on how the system identifies modified files using NTFS journal tracking, generates versioned backups, organizes storage targets, and manages data retention without significant system overhead.

Change Detection via the NTFS USN Journal

File History avoids the performance penalty of scanning every file individually by leveraging the NTFS Update Sequence Number (USN) Journal. Whenever a file on an NTFS-formatted volume is created, modified, or deleted, the file system logs this event as a record in the USN Journal.

During an automated backup cycle, the File History service queries the USN Journal rather than performing a complete drive crawl. By reading these journal records, the service quickly compiles a delta of only the files within monitored directories that have changed since the last backup operation.

Monitored Scopes and Execution Trigger

File History defaults to monitoring standard Windows User Profile directories:

  • Libraries (Documents, Music, Pictures, Videos)
  • Desktop
  • Contacts and Favorites
  • Custom user-defined folders

By default, an internal scheduler triggers the backup engine once per hour, though users can adjust the frequency from every 10 minutes to daily. If the target backup drive is disconnected, the service continues to track changes in the local catalog until the target becomes reachable again, caching temporary backup copies to the local system drive if configured to do so.

Versioning and File Storage Structure

Unlike conventional backup tools that bundle files into proprietary archives (like .vhd or .zip), File History stores files in an open, native format directly on the target storage device.

  1. Naming Convention: When a file is backed up, File History appends a UTC timestamp to the file name using the pattern: OriginalName (YYYY_MM_DD HH_MM_SS UTC).ext.
  2. Directory Structure: The backup drive mirrors the original folder tree under a designated path: [Drive]:\FileHistory\[Username]\[ComputerName]\Data\[DriveLetter]\.
  3. Data Integrity: Because files remain in their native formats, they can be recovered using standard File Explorer utilities without needing the File History restoration interface.

The Catalog Engine (ESENT Database)

To present a coherent timeline and handle file rollbacks, File History relies on a local database managed by the Extensible Storage Engine (ESENT). Located in the %LocalAppData%\Microsoft\Windows\FileHistory\Configuration\ directory, these catalog files (primarily Catalog1.edb and Catalog2.edb, paired with XML configuration files) maintain:

  • A mapping between original file paths and their versioned counterparts on the backup drive.
  • Checksums, timestamps, and file attributes.
  • Event logs indicating additions, edits, or deletions.

When a user browses historical versions of a folder, Windows queries this database to reconstruct the directory state as it existed at any specific snapshot point.

Data Retention and Maintenance

File History handles storage limits through retention policies defined by the user. Options range from keeping file versions indefinitely to purging older iterations after a set timeframe (e.g., 1 month to 2 years) or when disk space runs low.

When a retention cleanup occurs, the engine deletes the expired versioned files from the backup drive and updates the local ESENT catalog to reflect the removals, preventing broken references in the restore timeline.
