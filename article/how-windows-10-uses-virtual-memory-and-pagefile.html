How Windows 10 Uses Virtual Memory and Pagefile

This article provides an overview of how the Microsoft Windows 10 operating system manages virtual memory and utilizes the pagefile.sys architecture. It covers the fundamentals of virtual address spaces, the life cycle of memory pages, the working set model, and the underlying algorithms—including working set trimming, modified page writing, and page replacement—that govern how data moves between physical RAM and storage.

Virtual Address Space and Hardware Paging

Windows 10 provides every process with its own private virtual address space (VAS). On 64-bit systems, this flat address space theoretically spans up to 128 terabytes per process. The operating system, in conjunction with the processor's Memory Management Unit (MMU), maps these virtual addresses to physical memory addresses using page tables.

Memory is divided into fixed-size blocks called pages, which are typically 4 kilobytes (KB) in size on x86/x64 architectures. Each page can exist in one of two primary hardware states:

  • Valid (Resident): The virtual page maps directly to a physical frame in RAM.
  • Invalid (Non-resident): The page is not currently in physical RAM. Attempting to access an invalid page triggers a hardware page fault exception, handing execution over to the Windows Memory Manager.

The Working Set Model

To ensure fair allocation and efficient memory usage, the Windows 10 Memory Manager implements the Working Set model. A process's "Working Set" is the collection of virtual pages currently resident in physical RAM assigned to that specific process.

Windows 10 enforces dynamic working set boundaries:

  • Minimum Working Set: The minimum amount of physical memory guaranteed to the process.
  • Maximum Working Set: The threshold of physical memory a process can occupy before the operating system begins aggressively reclaiming its pages.

When physical RAM runs low, the operating system executes Working Set Trimming. It inspects processes that are idle or exceeding their operational needs and evicts eligible pages to make room for active workloads.

Page States and the Page Lists

Pages removed from a working set are not immediately written to disk. Instead, Windows tracks them using specialized software lists:

  1. Standby List: Contains clean pages (pages whose contents already match what is stored on disk or in the pagefile). These pages act as an in-memory cache. If the process requires the page again, a "soft page fault" occurs, instantly restoring the page to the working set without disk I/O.
  2. Modified List: Contains dirty pages whose contents have been modified since they were read from or written to disk. These pages must be written to backing storage before their physical RAM frames can be reused.
  3. Free List: Pages available for allocation that contain uninitialized or stale data.
  4. Zeroed List: Free pages that have been filled with zeros by a background system thread for security and fast allocation.

Page Replacement Algorithms

Windows 10 does not use a strict Least Recently Used (LRU) algorithm because true LRU requires high computational overhead to track every memory access. Instead, it employs an approximated LRU algorithm based on the Clock (FIFO with Second Chance) algorithm.

During working set trimming:

  1. The Memory Manager scans the Page Table Entries (PTEs) of a target process.
  2. Hardware sets an "Accessed" or "Referenced" bit in the PTE whenever a page is read or written.
  3. The algorithm inspects this bit:
    • If the bit is 1, the page has been accessed recently. The manager clears the bit to 0 and leaves the page in the working set (granting it a "second chance").
    • If the bit is 0, the page has not been accessed since the last scan. The manager removes the page from the process working set and pushes it to either the Standby List or the Modified List.

The Role of Pagefile.sys and the Modified Page Writer

The pagefile.sys file serves as a secondary storage extension of physical RAM for non-file-backed data (known as private or anonymous memory). Standard executable code and read-only mapped files are backed by their original locations on disk, but modified heap, stack, and dynamically allocated memory require the pagefile to persist when evicted from RAM.

Writing to pagefile.sys is handled by the Modified Page Writer (MPW), a set of high-priority kernel threads:

  • When the Modified List reaches a specific capacity threshold, the MPW wakes up.
  • It organizes dirty pages into contiguous physical disk sectors to minimize I/O fragmentation and maximize write throughput.
  • Once the write operation completes, the pages transition from the Modified List to the Standby List. Their physical frames remain cached until another allocation overwrites them.

Memory Compression in Windows 10

Windows 10 introduced an intermediate layer between RAM eviction and pagefile writes: the Compression Store.

When the system experiences memory pressure, the Memory Manager compresses inactive pages using an optimized LZ-based algorithm and stores them within a dedicated working set in the system process. Instead of incurring slow disk writes to pagefile.sys, pages are compressed in-memory. A subsequent request for that page triggers a soft decompression fault, which executes significantly faster than reading from a physical storage device. Only when the compressed store itself requires trimming are the compressed blocks serialized and written to the pagefile.
