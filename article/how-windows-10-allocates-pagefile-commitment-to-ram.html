How Windows 10 Allocates Pagefile Commitment to RAM

This article explains how the Microsoft Windows 10 operating system manages virtual memory commitments between physical RAM and the disk-based pagefile. In Windows 10, memory allocation is governed by the Virtual Memory Manager (VMM), which abstracts hardware memory into virtual address spaces. Rather than mapping commitments directly to physical chips on a one-to-one basis, the operating system uses demand paging, working set algorithms, and commitment limits to dynamically balance active data in physical RAM while reserving secondary storage space in the pagefile as an overflow guarantee.

Virtual Memory and the Commit Charge

When an application requests memory in Windows 10, it does not request physical RAM directly. Instead, it asks the Windows Virtual Memory Manager to "commit" a block of virtual memory.

  • Commit Limit: The total amount of virtual memory that the operating system can guarantee to all running processes combined. It equals the total size of physical RAM plus the maximum current size of all active pagefiles (pagefile.sys).
  • Commit Charge: The current sum of all allocated, promised memory across the system.

Windows enforces a strict rule: the total Commit Charge can never exceed the Commit Limit. However, committing memory does not immediately occupy physical RAM. When an allocation is committed, Windows simply guarantees that if the process writes data to those virtual pages, the system will have room to store it, either in RAM or on disk.

Demand Paging and Physical RAM Allocation

Physical RAM is allocated on a lazy evaluation model known as demand paging. The step-by-step process of how committed memory reaches physical RAM occurs as follows:

  1. Reservation and Commitment: A process requests memory via APIs such as VirtualAlloc using the MEM_COMMIT flag. At this stage, page table entries (PTEs) are created and marked as invalid (not yet in physical memory), and the system Commit Charge increases. No physical RAM frames are assigned yet.
  2. The Page Fault: When the application attempts to read from or write to the committed address for the first time, the CPU detects that the page is not mapped to physical RAM and triggers a hardware exception called a page fault.
  3. Frame Allocation: The Windows Memory Manager intercepts the page fault. It grabs a free physical page frame from its internal Free Page List or Zeroed Page List, maps the virtual address to this physical hardware frame, updates the process's page table, and allows the instruction to complete.
  4. Working Set Integration: Once resident in physical RAM, this page becomes part of the application’s Working Set (the set of pages currently resident in physical memory).

How the Pagefile Backs Committed Memory

The pagefile does not act as an active computing space; it is a backing store. Physical RAM handles active processing, while the pagefile guarantees that the system will not crash if the total commitment exceeds physical RAM capacity.

Windows treats physical RAM as a cache for the commit charge:

  • Private Committed Memory: Data created dynamically by applications (heaps, stacks, and private allocations) has no corresponding file on disk. These allocations are backed exclusively by the pagefile.
  • Overcommitting RAM: If a system has 16 GB of RAM and an 8 GB pagefile, the Commit Limit is 24 GB. Windows allows processes to commit up to 24 GB of total private data. As long as the actively accessed data (active working sets) fits within the 16 GB of RAM, system performance remains unaffected.

Working Set Trimming and the Modified Page Writer

When physical RAM runs low, Windows redistributes allocations through a process called working set trimming:

  1. Aging and Inactivity: The Memory Manager monitors page access via the CPU's accessed/dirty bits. Pages that have not been read or written to recently are prioritized for eviction.
  2. Transition to Standby or Modified Lists: Clean pages (pages that have not been altered or are already backed by a file on disk) are moved to the Standby List, where they can be discarded immediately if RAM is needed. Modified pages (pages containing altered private data) are moved to the Modified List.
  3. Writing to the Pagefile: The system background thread, known as the Modified Page Writer, writes dirty pages from the Modified List directly to pagefile.sys.
  4. Freeing RAM: Once written to disk, the page table entry is marked as transitioning, and the physical RAM frame is moved to the Standby List. If another process needs RAM, that physical frame is reassigned.

If the original process accesses that memory address again, another page fault occurs. The Memory Manager reads the page back from pagefile.sys, places it into an available physical RAM frame, and resumes the process seamlessly.
