Windows 10 DLL Search Order and Path Resolution

When an application running on Microsoft Windows 10 requests a dynamic-link library (DLL) without specifying a fully qualified file path, the operating system uses a deterministic search algorithm to locate and load the required file. This article outlines the specific sequence Windows 10 follows to resolve DLL locations, examines the default role of Safe DLL Search Mode, explains dynamic runtime modifications via the Windows API, and highlights the security implications of this process.

Known DLLs Check

Before initiating any disk-based directory search, the Windows 10 loader checks whether the requested DLL is already loaded in memory or listed as a "Known DLL." Known DLLs are defined in the Windows Registry under:

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs

If the library is found in this registry key, the operating system immediately redirects the search to the %SystemRoot%\System32 directory and bypasses all standard search paths.

Standard Search Order (Safe DLL Search Mode)

Windows 10 enables Safe DLL Search Mode by default. This security feature moves the Current Working Directory (CWD) further down the search sequence to reduce the risk of DLL preloading attacks.

When Safe DLL Search Mode is enabled, Windows 10 searches directories in the following order:

  1. The Application Directory: The directory from which the executing application was loaded.
  2. The System Directory: The Windows system directory, retrieved via the GetSystemDirectory function (typically C:\Windows\System32).
  3. The 16-Bit System Directory: A legacy compatibility path (typically C:\Windows\System).
  4. The Windows Directory: The main Windows operating system directory, retrieved via the GetWindowsDirectory function (typically C:\Windows).
  5. The Current Working Directory (CWD): The active directory context from which the process was initiated or changed programmatically.
  6. The PATH Environment Directories: The directories listed in the system PATH environment variable, followed by the user PATH environment variable.

If Safe DLL Search Mode is explicitly disabled via the registry (SafeDllSearchMode set to 0 under HKEY_LOCAL_MACHINE\System\CurrentControlSet\Control\Session Manager), the Current Working Directory is prioritized and searched immediately after the application directory (Step 1), before the System Directory.

Packaged Desktop and UWP Applications

For Universal Windows Platform (UWP) apps or desktop applications packaged via MSIX/AppX, Windows 10 restricts the search algorithm to protect containerized environments. The search checks:

  1. The package dependency graph (the application’s installation folder).
  2. Any explicitly specified dependencies in the package manifest.
  3. System directories containing OS binaries (System32).

Arbitrary search paths, including the Current Working Directory and the standard system PATH, are excluded from packaged application lookups.

Programmatic Control of DLL Search Paths

Developers can alter or constrain the default resolution behavior at runtime using specific Windows APIs:

  • SetDllDirectory: Adds a specific directory to the search path and removes the Current Working Directory from the standard search sequence.
  • SetDefaultDllDirectories: Restricts the dynamic search path strictly to defined subsets, such as LOAD_LIBRARY_SEARCH_APPLICATION_DIR, LOAD_LIBRARY_SEARCH_SYSTEM32, or directories added using AddDllDirectory.
  • LoadLibraryEx Flags: When loading libraries programmatically, passing flags such as LOAD_LIBRARY_SEARCH_DEFAULT_DIRS or LOAD_WITH_ALTERED_SEARCH_PATH forces the operating system to abandon the default sequence in favor of explicit, application-governed rules.

Security Implications: DLL Hijacking

Understanding the search path is critical for mitigation against DLL search order hijacking (or binary planting). If an application attempts to load a non-existent DLL or relies on locations specified late in the search order (such as the PATH variable), an attacker with write access to preceding directories (such as the CWD or application directory) can place a malicious DLL of the same name. Windows 10 then executes the malicious library under the security context of the host process. Adhering to Safe DLL Search Mode and explicitly declaring absolute file paths or restrictive search flags prevents this vulnerability.
