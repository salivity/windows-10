How Windows 10 Enforces Privilege Separation

This article explores how the Microsoft Windows 10 operating system strictly isolates standard user environments from high-privilege system services. By leveraging core architectural boundaries such as Session 0 isolation, Mandatory Integrity Control, Discretionary Access Control Lists, security access tokens, and Windows Service Hardening, Windows 10 ensures that standard user processes cannot tamper with or assume the identity of critical system components.

Session 0 Isolation

Windows 10 physically separates user interface tasks from system-level background processes through Session 0 isolation. In older versions of Windows, services and the first logged-on user shared Session 0, exposing services to interactive messaging attacks (such as "shatter attacks"). Windows 10 mitigates this by dedicating Session 0 exclusively to non-interactive system services and drivers. All user logons are assigned distinct sessions (Session 1, Session 2, and so forth). Because graphical user interface (GUI) message loops and window handles cannot cross session boundaries, code running in a standard user's desktop session cannot send arbitrary or malicious messages to services running in Session 0.

Access Tokens and Security Identifiers (SIDs)

Every process in Windows 10 runs within a security context defined by an access token. When a standard user logs on, the Local Security Authority Subsystem Service (LSASS) creates a restricted token containing the user’s Security Identifier (SID), group SIDs, and specific assigned privileges. System services run under specialized identities such as NT AUTHORITY\SYSTEM, NT AUTHORITY\LOCAL SERVICE, or NT AUTHORITY\NETWORK SERVICE.

Standard user tokens are stripped of critical operating system privileges (such as SeDebugPrivilege or SeTakeOwnershipPrivilege), meaning user-spawned processes cannot inspect memory, inject threads, or modify the state of processes owned by elevated service accounts.

Mandatory Integrity Control (MIC)

Mandatory Integrity Control enforces privilege boundaries regardless of traditional permissions. Windows 10 assigns an Integrity Level (IL) to securable objects (files, processes, registry keys) and access tokens:

  • Low: Sandboxed applications (e.g., restricted browser tabs).
  • Medium: Standard user processes.
  • High: Administrative processes running with elevated rights.
  • System: Windows operating system services.

Under MIC rules, a process with a lower integrity level cannot write to, alter, or terminate an object with a higher integrity level (No-Write-Up policy). Even if standard file permissions accidentally allow write access, a standard user process at Medium IL is blocked by the kernel from modifying a System IL service executable, process memory, or configuration.

Discretionary Access Control Lists (DACLs)

Securable resources—including system files, registry entries, named pipes, and service objects—are governed by Discretionary Access Control Lists (DACLs). The Windows Security Reference Monitor (SRM) validates every requested action against the target object's DACL.

Windows Service Controller objects, the Service Control Manager (SCM), and service binary paths are configured out-of-the-box with strict DACLs that permit standard users only query-related rights (such as SERVICE_QUERY_STATUS or SERVICE_QUERY_CONFIG). Rights to change configurations (SERVICE_CHANGE_CONFIG), stop services (SERVICE_STOP), or start sensitive services are withheld from standard users.

Windows Service Hardening (WSH)

To limit the blast radius should a service be compromised, Windows 10 implements Windows Service Hardening:

  • Per-Service SIDs: Rather than granting shared system accounts broad access to the entire operating system, services can be assigned a unique SID. Access to specific files, registry keys, and network ports is then granted strictly to that specific service SID rather than to NT AUTHORITY\SYSTEM globally.
  • Privilege Stripping: Services in Windows 10 explicitly declare the exact set of privileges they require to function. During service startup, the Service Control Manager strips away all unneeded privileges from the service’s access token, ensuring the service cannot be abused to perform unauthorized system operations.
  • Restricted Tokens: Network-facing services are often executed using restricted tokens that block access to sensitive local resources entirely, even if the service process is somehow hijacked.
