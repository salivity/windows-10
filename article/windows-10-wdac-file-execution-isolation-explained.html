Windows 10 WDAC File Execution Isolation Explained

Windows Defender Application Control (WDAC) in Windows 10 isolates and restricts file execution by shifting the operating system from a traditional "trust by default" model to a zero-trust, allowlist-only architecture. Rather than relying on reactive threat signatures to detect known malicious software, WDAC validates every driver, executable, dynamic-link library (DLL), and script against strict cryptographic policies before code can load into memory. By coupling these policies with hardware-enforced virtualization, WDAC isolates the core operating system from unauthorized, modified, or unvetted code execution.

Kernel-Level Code Integrity (CI) Verification

WDAC operates primarily through the Windows Kernel Code Integrity (ci.dll) subsystem. Whenever a file execution request occurs—whether an administrative utility, a third-party application, or a kernel driver—the Code Integrity module intercepts the request before memory allocation occurs.

The system validates the target file against defined rules within the active binary Code Integrity policy (SIPolicy.p7b). If a file fails to match any allow rule, the kernel denies execution immediately, returning an "Access Denied" error to the calling process and logging an event to the Code Integrity operational event log.

Virtualization-Based Security (VBS) and HVCI

To ensure attackers cannot disable WDAC by tampering with the kernel, Windows 10 integrates WDAC with Virtualization-based Security (VBS) and Hypervisor-Protected Code Integrity (HVCI).

  • Virtual Trust Level 1 (VTL 1): VBS uses the Windows Hypervisor to create an isolated execution environment separate from the standard operating system (VTL 0).
  • Secure Kernel Execution: The Code Integrity verification engine runs inside this isolated VTL 1 space.
  • Memory Protection: Even if an attacker gains full kernel privileges in VTL 0, hardware page-table protections prevent them from altering WDAC policies or executing memory pages that have not been signed and verified by the VTL 1 hypervisor layer.

Cryptographic Rule Evaluation

WDAC does not simply rely on easily manipulated metadata like file names. Instead, it evaluates binary files based on robust, tamper-resistant criteria:

  1. Digital Certificates: Policies define trusted Root and Intermediate Certification Authorities (CAs). Files signed by trusted certificates (such as internal enterprise PKIs or Microsoft) are allowed to run.
  2. Publisher and Versioning: Rules can enforce specific publisher details and require minimum file versions, preventing attackers from executing vulnerable, older versions of legitimate software (known as binary downgrade attacks).
  3. Cryptographic Hashes: For unsigned or standalone utilities, WDAC calculates the file's SHA-256 flat hash or authenticode page hash to guarantee execution of that exact binary only.
  4. Well-Known Reputations (ISG): Policies can integrate with the Microsoft Intelligent Security Graph (ISG) to automatically permit files deemed trustworthy by global telemetry.

Constrained Language Mode for Scripting Engines

Executable isolation extends beyond compiled .exe and .dll binaries. Scripting languages and runtime environments represent a common bypass vector for binary-level controls.

When WDAC is active, Windows 10 automatically forces script hosts—including PowerShell, Windows Script Host (cscript.exe/wscript.exe), and Microsoft HTML Applications (mshta.exe)—into Constrained Language Mode (CLM). Under CLM:

  • Arbitrary API calls, COM object instantiations, and unapproved .NET types are strictly blocked.
  • PowerShell scripts must be digitally signed according to the WDAC policy to run in Full Language Mode.
  • Unsigned scripts are either blocked entirely or restricted to simple commands, neutralizing memory-injection and living-off-the-land techniques.
