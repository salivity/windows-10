How Windows 10 Handles Per-App Audio Routing

Windows 10 features a native audio management system that allows users to route audio streams from individual applications to specific hardware playback and recording devices. Introduced in the Windows 10 April 2018 Update (Version 1803), this functionality enables independent audio streams—such as routing a web browser through desktop speakers while directing a voice communication app through a headset—without requiring third-party software.

The Audio Subsystem and WASAPI

At the core of Windows 10 audio handling is the Windows Audio Session API (WASAPI). WASAPI provides application-level communication with the Windows audio engine and the underlying hardware drivers.

When an application plays or records sound, it opens an audio client session with WASAPI. In earlier versions of Windows, all applications using shared-mode audio were bound to a single system-wide "Default Device." In Windows 10, the core audio engine intercepts these audio sessions and maps individual processes to specific audio endpoint identifiers (Device IDs), overriding the global default without affecting the rest of the operating system.

The Routing Interface

Windows 10 exposes this routing capability through the App volume and device preferences menu (located in Settings > System > Sound).

Within this interface, Windows lists every application currently running an active audio session. Alongside volume sliders, each application presents two drop-down selectors:

  • Output: Selects the playback device (e.g., headphones, external speakers, HDMI audio).
  • Input: Selects the capture device (e.g., internal microphone, USB headset, auxiliary input).

Leaving an option set to "Default" directs the application to follow whichever device is currently designated as the system default. Selecting a specific device locks the application's audio session to that endpoint.

Persistence and Registry Tracking

When a user assigns an application to an audio device, Windows 10 writes the preference to the registry, binding the executable's path to the specific endpoint GUID (Globally Unique Identifier) of the hardware.

Because of this registry mapping:

  • The assignment persists across application restarts and system reboots.
  • Assignments are process-specific: running multiple instances of the same application generally inherits the same routing rules.
  • An application must produce or request an active audio stream at least once to register with the Windows audio mixer before it appears in the routing interface.

Device Disconnection and Fallback Behavior

Windows 10 dynamically monitors the state of audio endpoints through Plug and Play (PnP) notifications. If an assigned audio device is disconnected (for example, unplugging a USB headset or disconnecting a Bluetooth speaker), Windows automatically falls back to the system's global default device to prevent the audio stream from terminating or hanging the application.

When the configured device is reconnected, the operating system detects its hardware GUID and immediately redirects the application's audio stream back to the assigned device without requiring an application restart.

Application-Level vs. OS-Level Control

While Windows 10 manages routing at the OS level, some applications (such as digital audio workstations, media players, and Discord) maintain their own internal device-selection settings.

If an application provides internal routing:

  • Using an exclusive mode (Exclusive WASAPI or ASIO) bypasses the Windows audio mixer entirely, taking direct control of the hardware.
  • Selecting a specific device inside the application's internal settings overrides the OS-level routing for that process.
  • Setting the application's internal setting to "System Default" allows the Windows 10 App volume and device preferences menu to fully control the audio destination.
