How Windows 10 Enforces MAC Using System Tokens

This article examines how the Microsoft Windows 10 operating system implements Mandatory Access Control (MAC) through its Mandatory Integrity Control (MIC) architecture. It details how security access tokens store integrity levels, how the Security Reference Monitor (SRM) enforces access restrictions, and how system tokens isolate critical operating system resources from unauthorized modification regardless of user permissions.

The Foundation: Windows Access Tokens and Integrity Levels

Windows 10 assigns an access token to every process and thread running in the operating system. Created during authentication by the Local Security Authority Subsystem Service (LSASS), this token serves as the definitive security context for execution. It contains the user’s Security Identifier (SID), group SIDs, assigned privileges, and an Integrity Level (IL) represented as a mandatory label SID.

Windows 10 defines six primary integrity levels:

  • Untrusted: Reserved for processes running in an anonymous or restricted sandbox.
  • Low: Used for internet-facing applications, such as sandboxed web browsers.
  • Medium: The default level assigned to standard user accounts and un-elevated processes.
  • High: Assigned to elevated processes run by administrators via User Account Control (UAC).
  • System: Assigned to core operating system services, drivers, and the Local System (NT AUTHORITY\SYSTEM) account.
  • Installer: The highest level, reserved for trusted software installation routines capable of altering system files.

Mandatory Integrity Control (MIC) Enforcement

While Windows natively uses Discretionary Access Control Lists (DACLs) to determine permissions, Mandatory Integrity Control operates as a mandatory security layer evaluated before DACL evaluation. Every securable object (such as files, registry keys, named pipes, and processes) contains a mandatory label stored within its System Access Control List (SACL).

When a process attempts to interact with an object, the kernel-level Security Reference Monitor (SRM) performs the access validation using the following mandatory policies:

  1. No-Write-Up: A process with a lower integrity level cannot write to, modify, or delete an object with a higher integrity level. Even if an object’s DACL grants write access to Everyone, an access token with a Medium integrity level is denied write access to a High or System integrity object.
  2. No-Read-Up: While read access across integrity levels is generally allowed to maintain compatibility, specific objects can enforce a No-Read-Up policy to block lower-integrity tokens from viewing sensitive data.
  3. No-Execute-Up: A process cannot inject code or execute routines inside a target process running at a higher integrity level.

System Tokens and Process Isolation

System-level processes—such as csrss.exe, services.exe, and lsass.exe—operate with access tokens assigned the System integrity level. Because standard user and elevated administrative processes execute at Medium and High levels respectively, the SRM blocks lower-integrity threads from obtaining handles with write or execution privileges (such as PROCESS_VM_WRITE or PROCESS_CREATE_THREAD) on system-level processes.

Through this strict hierarchical token enforcement, Windows 10 prevents malware or exploited applications operating in lower-privilege contexts from tampering with critical kernel services, modifying core system binaries, or hijacking system tokens to achieve privilege escalation.
