Role of LSASS in Windows 10 Explained

The Local Security Authority Subsystem Service (LSASS) is a core process in the Microsoft Windows 10 operating system responsible for enforcing security policies, managing user authentication, and creating access tokens. This article provides a concise overview of what LSASS does, how it interacts with system components, and why its integrity is critical to the overall security of Windows 10.

User Authentication

LSASS runs as a protected system process named lsass.exe. When a user attempts to sign in to a Windows 10 machine—whether locally or via a network domain—LSASS handles the verification of the submitted credentials. It interfaces with authentication packages such as NTLM (for local and legacy authentication) and Kerberos (for Active Directory environments).

When logging in locally, LSASS queries the Security Accounts Manager (SAM) database to verify user credentials. If the system is joined to a domain, LSASS communicates with the domain controller to validate the user through Kerberos tickets.

Access Token Creation

Once credentials are successfully verified, LSASS generates an access token for the authenticated user. This access token contains:

  • The user’s Security Identifier (SID)
  • Group SIDs representing the user’s group memberships
  • Privileges assigned to the user account (such as the ability to shut down the system or take ownership of files)

Every application, process, or thread launched by the user inherits a copy of this access token. The Windows kernel uses this token to grant or deny access to system resources, files, and registry keys.

Security Policy Enforcement

LSASS is responsible for managing and enforcing the Local Security Policy on Windows 10. It controls:

  • Password policies (minimum length, complexity requirements, and expiration)
  • Account lockout thresholds
  • User rights assignments (e.g., "Log on as a service" or "Allow log on locally")
  • System audit policies, ensuring that security-related events (such as failed login attempts) are written to the Windows Security Event Log

Credential Caching and Single Sign-On (SSO)

To provide Single Sign-On (SSO) functionality, LSASS stores active credentials and tickets in its process memory. This allows users to access network shares, printers, and internal websites without repeatedly entering their username and password during an active session.

Security Implications and Protection in Windows 10

Because lsass.exe stores credentials in memory, it is a primary target for credential dumping tools such as Mimikatz. If an attacker gains administrative privileges, extracting credentials from LSASS memory can lead to lateral movement across a network.

To mitigate this risk, Windows 10 includes advanced protective measures:

  • LSA Protection (RunAsPPL): Configures LSASS to run as a Protected Process Light (PPL), preventing unsigned drivers or non-protected processes from reading its memory space.
  • Credential Guard: Uses Virtualization-Based Security (VBS) to isolate credential secrets inside a secure virtual container (Virtual Secure Mode), completely removing the secrets from the standard LSASS memory accessible by the host operating system.
